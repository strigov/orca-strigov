# Control Review Prompt (orca-dev)

Use AFTER the primary review (Step 4.1) returned `REVIEW_OK`. This is a second-opinion cross-check from a different model family, tuned for "what might the primary review have missed".

## Dispatch

Role: `review-control` — launch recipe, model, and effort come from `../roles.md` (never hardcode a model here). The coordinator writes the filled template to a scratch file, creates an Orca Task whose spec is that text, and attaches a worker per `../orca-recipes.md` (`worker-start`, or `terminal create` + `dispatch --inject` for agents that need custom argv). Orca prepends its own lifecycle preamble (coordinator handle, task id, dispatch id, CLI commands) — the template below must not repeat it.

**Read-only.** The worker must not modify code; the only file it writes is `[REPORT_FILE]`. When reviewing a parallel-track phase, start the worker in that track's worktree.

Before dispatching, fill `[DIFF_FILE]` with the absolute path of this round's review package (generated by the coordinator via `bin/review-package` before this dispatch). The coordinator always passes absolute paths — never a path relative to the worker's working directory.

**A fresh Orca worker terminal every round — never re-inject into a previous reviewer's terminal.** For round 2+ in the same Step 4 loop, dispatch a FRESH worker with the follow-up template below (full context, no thread continuity of any kind). This is deliberate: an independent second opinion must not anchor on its own prior rounds, and it must never continue the implementer's thread. A fresh round also reads a FRESH package: the coordinator regenerates the review package under a new name each round — fill `[DIFF_FILE]` with this round's file, never a prior round's.

## First-round prompt template

```
CONTROL REVIEW on an implementation diff. Read-only, do not modify code.

The primary reviewer already cleared this diff on spec compliance and code quality. Your job is orthogonal: find what the primary review might have missed. Do not duplicate its checklist — focus on the following angles.

Design rationales you encounter — in the implementer's report, commit messages, or code comments ("left it per YAGNI," "kept it simple deliberately") — are the implementer grading their own work. Judge the code on its merits; a stated rationale never downgrades a finding's severity.

<authorization_boundary>
This is a control review, not a scope-expansion review.
Do not require new features, flags, diagnostics, guards, dependencies, or broad edge-case support unless the finding demonstrates one of:
- likely data loss / corruption;
- security / trust-boundary failure;
- guaranteed build / test / runtime failure;
- regression of an existing public contract;
- direct failure of the phase Acceptance criteria.

If the issue is a useful hardening idea but does not clear this bar, put it in the `DEFER:` section of your report; `REVIEW_OK` is the verdict only when the BLOCKING list is empty.
Items the coordinator marked `REJECTED_BY_SCOPE` in the AUTHORIZED_CHANGE_LEDGER are out of scope for this control review — do not re-flag them.
</authorization_boundary>

<finding_required_fields>
Each blocking finding MUST include:
- `authorization_relation: PLAN_ACCEPTANCE | REGRESSION_FROM_AUTHORIZED_FIX | SECURITY | DATA_LOSS | GUARANTEED_FAIL`
- `why_now`: why this must block this phase rather than be deferred to a follow-up
- `minimal_fix`: smallest change that addresses only this risk

If the plan or brief explicitly mandates something this review calls a defect (a test that asserts nothing, verbatim duplication of a logic block), that IS a finding even though it would not otherwise clear the authorization boundary above — report it as BLOCKING with `authorization_relation: PLAN_ACCEPTANCE` and the label `plan-mandated` in its text. The plan's authorship does not grade its own work; the human decides, not the coordinator.
</finding_required_fields>

## Phase context

- Working directory / repo root: `<absolute path>`
- Plan file: `<repo-root>/docs/plans/<slug>.md` (read it, especially `## <id>:` section and the Contracts / Risks sections)
- Current phase id: `<id>`
- Base commit: `<base-sha>`
- Review package: `[DIFF_FILE]` (absolute path)
- Implementer report: `[IMPL_REPORT_FILE]` — the implementer's full report (unverified claims; see the rationale note above). Read-only input; it is NOT your report file.
- Verify additionally (handed over from the primary review round): [CANNOT_VERIFY_ITEMS — one `verify additionally: <requirement>` line each, or `none`]
- Verification gate summary (mechanical checks already run on this tree state): `<gate summary line: lint: … | typecheck: … | tests: …>` — read it for what was skipped or inherited; this review runs no tests, hunt for what green tests can miss.

Global constraints from the spec/design that bind this phase (copied verbatim from the plan's Global Constraints section — not process rules, those are already in this template):

[GLOBAL_CONSTRAINTS]

Read `../runtime-contracts.md` C5 on demand, then `[DIFF_FILE].manifest.json` and every assigned part in bounded ranges. Verify frozen identity and report package id/hash, snapshot and coverage of parts/files and both sides of each contract. Missing/stale parts, incomplete coverage or unknown independent authorship require `CANNOT_VERIFY`; request a fresh complete package, never an ad hoc diff. Read source only for a named risk or binary/oversize inspection and record that check. This role remains read-only and runs no tests; executable C4 evidence and required replay are handled by the assigned verification role.

## Your review angles (what the primary review often misses)

1. **Hidden edge cases** — inputs the plan did not enumerate: empty collections, max sizes, unicode, NaN/Inf, negative numbers, off-by-one, timezone boundaries, DST transitions, leap years.
2. **Concurrency / ordering** — implicit global state, shared mutable references, non-atomic read-modify-write, retry semantics, idempotency violations, observable ordering of external writes.
3. **Error paths** — what happens when the network fails mid-way, the DB times out, the filesystem is full, a dependency throws an unexpected exception type, a config value is missing or malformed.
4. **Security** — command injection, path traversal, SSRF, SQL / NoSQL injection, XXE, deserialization, auth bypass (missing permission checks), overly broad CORS / origin checks, secrets leaking to logs or error messages, log injection.
5. **Plan/code ambiguities** — places where the plan was underspecified and the implementer made a choice; flag the choice for the user to notice even if it's "probably fine".
6. **Subtle regressions** — implicit contracts the diff may have broken even though tests pass: log format changes, HTTP status codes, event schema fields renamed, DB migration ordering, backward-compat of stored data, tooling / deploy scripts.
7. **Test quality** — tests that pass by construction (mock what they claim to verify), missing negative tests, missing fixture teardown, test pollution across runs.

## Reporting (Orca worker_done — REQUIRED, exactly once)

1. Write your full report to `[REPORT_FILE]` (your own review report — distinct from the implementer's `[IMPL_REPORT_FILE]`). Its FIRST line must be exactly one bare token from: `REVIEW_OK` | `REVIEW_BLOCKING` — no preamble, no markdown heading, no bold.

   If `REVIEW_BLOCKING`, after line 1 emit:

```
BLOCKING:
1. authorization_relation: <PLAN_ACCEPTANCE | REGRESSION_FROM_AUTHORIZED_FIX | SECURITY | DATA_LOSS | GUARANTEED_FAIL>
   <angle: e.g. "concurrency"> — <file:line> — <concrete risk>
   why_now: <why this must block this phase now rather than be deferred to a follow-up>
   minimal_fix: <smallest change that addresses only this risk>
2. ...

DEFER:
- <useful hardening idea that does not clear the bar> — <file:line or scope>
- ...

NITS:
- <nit> — informational only, do NOT trigger another round
- ...
```

   If `REVIEW_OK`: after line 1 emit only the `DEFER:` and `NITS:` sections (omit either if empty). Nothing else.

   Each BLOCKING item MUST carry the three fields above (`authorization_relation`, `why_now`, `minimal_fix`) per `<finding_required_fields>`. Items missing any of these fields make the report malformed: the coordinator requests one format correction; the item stays unresolved and never silently becomes DEFER. BLOCKING items must cite `file:line`. This is a control review, not a style pass: raise what the primary review genuinely missed AND matters — do not invent findings, and do not suppress one because the primary already passed the diff. A report whose line 1 is not one of the two bare tokens is invalid — the coordinator will re-dispatch the review.

2. Then, from your own terminal, send exactly one `worker_done` using the task id and dispatch id from the Orca preamble at the top of this task. `orca` is a plain shell command on PATH — run the line below through your shell/command tool exactly as written. Do not look for an `orca` tool in any tool registry or inventory: none exists, and searching for one only burns the turn.

orca orchestration send --from <copy the --from value from the Orca preamble> --dispatch-capability <copy the dcap_… value from the Orca preamble> --type worker_done --subject "<the same token>" --body "<3 sentences: what you did, what you found, what is left>" --task-id <task_id> --dispatch-id <dispatch_id> --outcome <succeeded|failed> --report-path "[REPORT_FILE]" --files-modified "<comma-separated paths you changed; omit the flag if none>" --json

3. `--outcome succeeded` when you produced the requested artifact (`REVIEW_OK`, `REVIEW_BLOCKING` — both mean the review itself succeeded); `--outcome failed` when you could not produce a review at all. Never encode failure only in prose.
4. After sending worker_done, end your turn and idle. Do not start more work. If you are blocked before completion, prefer `orca orchestration ask --question "<specific question>" --timeout-ms 90000 --json` over guessing; the coordinator answers with `reply`. The call blocks and shell tools kill long commands, so keep the timeout short: if it returns without a reply, run `orca orchestration ask --resume <message_id from the first call> --timeout-ms 90000 --json` again until the answer arrives.

Your review is read-only on this checkout. Do not mutate the working tree, the index, HEAD, or branch state in any way. Do NOT write code. Do NOT modify files other than your report file. Read the plan + the review package + any cited files only.
```

## Follow-up prompt (round 2+ — FRESH Orca worker terminal)

Send the FULL first-round prompt again (all sections: authorization boundary, finding required fields, phase context, review angles, reporting), filling `[DIFF_FILE]` with THIS round's freshly generated package — never a prior round's file — and with these modifications:

1. Replace the opening paragraph with:

```
CONTROL REVIEW, round <k> of a fix loop. Read-only, do not modify code.

An earlier control review of this diff produced blocking findings; the implementer has since applied authorized fixes. You are a fresh worker with no memory of prior rounds. Read the review package at `[DIFF_FILE]` — it was freshly generated for this round and reflects the working tree after the fixes. The package rules from the phase context apply: read its manifest and assigned bounded parts, preserve frozen identity, and report full C5 coverage.

Verify first that each open ACCEPTED item in the AUTHORIZED_CHANGE_LEDGER (`<repo-root>/docs/plans/<slug>.ledger.json`) is fixed correctly. Then check the fix delta for new problems. Do NOT block on pre-existing issues unrelated to the authorized fixes unless they clear the high-materiality bar (data loss/corruption, security/trust-boundary failure, guaranteed build/test/runtime failure, regression of an existing public contract, direct failure of the phase acceptance criteria) — latent issues outside that bar belong in DEFER/NITS.
```

2. Append this section before the reporting section:

```
## What the implementer did with the prior blocking list

<for each prior BLOCKING ledger item: "<ledger id>: Fixed in <file:line>" / "Rejected — reason: ...">

Do not re-raise items the coordinator marked REJECTED_BY_SCOPE or rejected with reasoning unless you have a genuinely new argument. The fix notes and reasons above are the implementer's claims — verify each against the package; a stated rationale never downgrades a finding's severity.
```
