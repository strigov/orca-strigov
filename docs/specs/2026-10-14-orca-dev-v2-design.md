# orca-dev v2 («orca-dev-lite»): спека дизайна

Дата: 2026-10-14. Репозиторий: `/Users/strigov/Documents/Claude/Projects/projects-code/orca-strigov`. Версия плагина после реализации: 2.0.0.

## Почему

Плагин 1.1.0 ломается на простых задачах. Последний случай (репозиторий Bureau): слияние двух уже принятых, бесконфликтных веток простояло больше часа в C6 `HOLD H1` (ждали доказательств семейства модели между Run'ами), породило 224 файла артефактов на 116 МБ, брифы ушли воркерам с незаполненными `<…>`, а координатор каждые ~90 с печатал одну и ту же строку статуса.

Причина структурная: плагин дублирует жизненный цикл Orca собственной машиной состояний (`bin/lib/protocol_state.py` + `protocol_facts.py`, ~1700 строк), квитанциями, ledger'ом, хешами и хуками, которые запрещают координатору завершать ход. Каждая проверка может уйти в HOLD, и ни одна не имеет выхода «сделать по-простому».

Orca 1.4.224 (`/Applications/Orca.app/Contents/Resources/bin/orca`) уже умеет всё нужное: `orca orchestration` (run-create/run-use, task-create, worker-start, dispatch --inject, check --wait, ask/reply, worker-list/show/read/stop/release) и штатные скиллы `orchestration` и `orca-cli` (`orca skills install`, `orca skills get`, `orca skills update`). Плагин должен быть тонким слоем над ними: пайплайн, пресеты моделей, рецепты запуска. Ничего больше.

## Цели и вне скоупа

Цели:

1. Разработка по SDD: спека с проверяемыми критериями приёмки (стиль Kiro) → план по фазам → TDD-исполнение → двойное ревью каждой фазы → финальное ревью ветки (цепочка Superpowers).
2. Ни одной ситуации без выхода: любой кап или сбой заканчивается объявленным фоллбэком или одним вопросом пользователю с вариантами.
3. Один `SKILL.md`, который работает координатором и в Codex, и в Claude Code.
4. Жизненный цикл воркеров целиком у нативного гайда Orca; наш код — два кроссплатформенных Python-файла: `bin/orca_dev.py` (подкоманды `brief`, `spawn`, `ready`, `close`) и `install.py` (один исходник для macOS/Linux/Windows, без bash-обёрток и `.ps1`-близнецов). Все хрупкие места — подстановка брифа, передача многострочного текста в `--spec`, сборка argv агента, подтверждение закрытия — внутри Python, не в shell координатора.
5. Экономия диска: работа в текущем checkout, без новых worktree и служебных папок.
6. Windows (native, PowerShell-координатор в Orca) поддерживается тем же кодом; платформенные различия — короткий раздел в `launch.md`.

Вне скоупа:

- Параллельные фазы в worktree, бридж `chatgpt-web/pro`, профили планирования, роли gate/synthesizer/diagnosis/quickfix/integration-check.
- Публикация в marketplace (release-скрипты и workflows удаляются; плагин ставится из checkout как personal plugin).
- Автоматическая чистка кэша плагинов Codex и `.superpowers/` в целевых репозиториях (только предупреждение и вопрос).

## Архитектура и состав файлов

Три слоя:

1. Нативный Orca: `orca orchestration` + штатные скиллы `orchestration` и `orca-cli` (ставятся `orca skills install`, обновляются `orca skills update`). Координатор читает их в начале каждой сессии через `orca skills get orchestration` (и `--reference references/<file>.md` по мере надобности). Воркерам хватает нативного преамбула (обязанности воркера: `check`, `ask`, `worker_done`).
2. `orca-dev` (наш скилл): пайплайн, жёсткие правила, капы, матрица ролей, рецепты запуска, брифы.
3. Два Python-файла (3.10+, только стандартная библиотека, все вызовы `orca` через `subprocess.run([...])` списком аргументов, UTF-8, без shell): `bin/orca_dev.py` и `install.py`. Вызов: macOS/Linux `python3 <plugin>/bin/orca_dev.py <подкоманда> …`, Windows `py -3 <plugin>\bin\orca_dev.py <подкоманда> …` (или `python`). Python 3.10+ на Windows — новое требование по сравнению с 1.1.0 (там хватало PowerShell 5.1).

Подкоманды `orca_dev.py`:

| Подкоманда | Что делает | Коды выхода |
|---|---|---|
| `brief <template> [KEY=VALUE …] [--set-file KEY=<path> …] --title <t> [--run <id>] [--dry-run]` | Заполняет шаблон (контракт п. 3 правил), затем `orca orchestration task-create --spec <text> --task-title <t> [--run <id>] --json`; печатает `task_id`. Многострочные значения (отчёт ревью, замечания) — через `--set-file`. `--dry-run` печатает заполненный бриф и Task не создаёт (для тестов) | 0 ok; 1 lint/незаполненный токен; 2 usage/неизвестный KEY; 3 отказ `orca` |
| `spawn --agent agy\|codex\|claude --model <m> [--effort <e>] --title <slug/роль-фаза> --task <task_id> [--worktree active] [--env KEY=VALUE ...]` | Собирает argv агента по правилам `launch.md` (с `--env` — префикс `env KEY=VALUE …`, только POSIX; на Windows код 2), `orca terminal create --worktree active --title <t> --command <argv-строка, собранная под ОС> --json` → `terminal wait --for tui-idle --timeout-ms 180000` → `ready` → `orca orchestration dispatch --task <id> --to <h> --inject --retry-request <сгенерированный id> --json`. Таймаут `ready` по агенту: agy 180 с, codex 120 с, claude 90 с. Известные модалки (таблица в `launch.md`) `spawn` снимает сам и перечисляет в `dismissed`. Всегда печатает один JSON, и при сбое тоже: `{stage, handle, task_id, dispatch_id, request_id, dismissed, agent, screen, error}`, `stage ∈ terminal_create \| ready \| dispatch \| done`, неизвестные значения — `null`/`[]`, `error` — исходное сообщение Orca, `screen` — последние строки экрана при кодах 1/5/6 | 0 done; 1 агент не готов за таймаут (`handle` заполнен — координатор делает `close` и один повтор); 2 usage; 3 `terminal create` упал (агент не запустился, задача никому не доставлена); 4 `dispatch` упал или исход неизвестен (`handle` заполнен; задача могла дойти до агента) — фоллбэк модели по коду 4 запрещён, разбор в §«Сбои»; 5 `blocked` — неизвестная модалка (`handle`, `screen`); 6 `needs_login` — экран входа (`handle`, `agent`) |
| `ready <handle> <agy\|codex\|claude\|marker> <timeout>` | Порт `wait-agent-ready` (поведение закреплено в таблице состава) плюс распознавание модалок и экранов входа по таблице `launch.md`: известную модалку снимает (`orca terminal send`) и ждёт дальше; таймаут — явный аргумент | 0 готов (stdout: JSON `{dismissed}`); 1 таймаут; 2 usage; 3 пять неудачных `terminal read` подряд; 5 неизвестная модалка; 6 экран входа |
| `close <handle>` | `orca terminal close --terminal <h> --json`, затем подтверждение: `ptyKilled: true` в receipt или отсутствие handle в `orca terminal list --worktree current --json` | 0 закрыт; 1 не подтверждено |

## Пайплайн

Шаг 0. Старт. `orca skills get orchestration`; `orca status --json` (runtime `ready`); `run-create --objective "<slug или задача>"` или `run-use --id <orca_run>` при возобновлении; закрыть отработавшие терминалы своего Run (§«Правила координатора» п. 9). Новая задача (плана ещё нет) при грязном `git status` → один вопрос «закоммитить как есть / отложить (`git stash`) / стоп» — это единственное место, где stash допустим. Возобновление — по алгоритму §«Состояние и возобновление».

Шаг 1. Триаж. Быстрый путь, если выполняются все условия: ≤2 файлов кода по оценке координатора, нет изменений схем/миграций/безопасности/публичных API. Сюда же входит слияние уже принятых веток. Иначе полный путь. Решение сообщается пользователю одной строкой вместе с первым dispatch'ем.

Быстрый путь: исполнитель (бриф `implementer.md`, роль «Исполнитель») → `worker_done` → координатор: `git diff` + проверки, которые сам назначил в брифе (тесты/линт проекта) → ревью Opus (`review-spec.md`, критерий — формулировка задачи) → ревью Astra (`review-quality.md`) → коммит → закрыть терминалы → итог пользователю. Фиксы и капы как у фазы (шаги 4–5).

Подпуть «слияние уже принятых веток»: координатор сам (git-операции ему разрешены) выполняет `git rev-parse HEAD`, запоминает напечатанный SHA (далее `<base-sha>`, подставляется буквально) и выполняет `git merge --no-ff <ref>` для каждой ветки по порядку. Конфликт → `git merge --abort` этой ветки, и её слияние с разрешением конфликтов уходит исполнителю как обычная задача быстрого пути (исполнитель коммитит merge-коммит сам). После всех слияний: проверки проекта, ревью Opus → Astra по `git diff <base-sha>..HEAD` (список коммитов — `git log --oneline <base-sha>..HEAD`); `blocking` → фиксы исполнителем дополнительными коммитами, повторное ревью; если ревью чистое и фиксов не было — дополнительных коммитов нет, итог пользователю со списком merge-коммитов.

Шаг 2. Спека (полный путь). Координатор сам ведёт короткий диалог с пользователем: по одному вопросу за сообщение, только то, без чего спеку не написать (обычно 1–3 вопроса). Затем бриф `spec-writer.md` → Opus `xhigh` пишет `docs/specs/<YYYY-MM-DD>-<slug>.md` с разделами: Цель; Вне скоупа; Критерии приёмки — пронумерованные `AC1…`, каждый в форме «КОГДА <условие>, ТОГДА <наблюдаемый результат>»; Дизайн (архитектура, файлы, интерфейсы). Astra `xhigh` ревьюит (`spec-review.md`): замечания списком с id; правит тот же Opus в своём терминале на `high` (`spec-revise.md`); кап 3 раунда. Чистое ревью → координатор показывает пользователю ссылку на файл и критерии приёмки и ждёт «ок». Это единственная обязательная остановка.

Шаг 3. План. Бриф `plan-writer.md` → Opus `xhigh` пишет `docs/plans/<slug>.md`:

```yaml
---
spec: docs/specs/2026-10-14-<slug>.md
orca_run: run_xxxxxxxxxxxx      # вписывает координатор перед dispatch'ем
status: active                  # active | done — ставит координатор
phases:
  - id: F1
    title: Хранилище
    risk: none                  # none | risky — risky: безопасность, данные, миграции, конкурентность
    area: backend               # backend | frontend
    hard: false                 # true — автор плана считает фазу заведомо сложной → исполнитель Sol с самого начала
    implementer: gemini         # gemini | luna | sol | opus | sonnet — текущий исполнитель; ставит координатор при запуске, фоллбэке и эскалации
    covers: [AC1, AC2]
    verify:
      - pytest tests/test_storage.py -q
      - ruff check src/
    status: pending             # pending | done — ставит координатор
---
```

Тело: по одному `## F<n>: <title>` на фазу — что сделать, какие файлы, какие тесты написать первыми, что закрывает. Каждый критерий спеки покрыт хотя бы одной фазой; фаза без `covers` недопустима. Обычно 1–5 фаз. Автор плана `implementer` не заполняет; координатор вписывает его при запуске исполнителя фазы (`gemini`, или `sol` для `hard: true`, или `opus`/`sonnet` для `area: frontend`) и меняет при фоллбэке/эскалации. Между коммитами фаз эта правка plan-файла остаётся незакоммиченной и попадает в коммит фазы. Astra `xhigh` ревьюит (`plan-review.md`, кап 4); правит тот же Opus на `high` (`plan-revise.md`). После чистого ревью координатор вписывает `orca_run`, коммитит спеку и план (`docs: spec + plan for <slug>`) и идёт к фазе F1; пользователю — краткая сводка (число фаз, их названия). Если пользователь заранее просил показать план — остановка на «ок».

Шаг 4. Фаза. Бриф `implementer.md` (в нём: путь к спеке и плану, id фазы, её `covers`, `verify`, требование TDD: сначала тест на критерий, потом код; запрет трогать файлы вне фазы без упоминания в отчёте). После `worker_done` координатор: `git diff --stat`, затем каждая команда `verify`. Красное или ошибки в отчёте → `fix-round.md` тому же исполнителю в тот же терминал (`dispatch --inject`). Технические фиксы и фиксы по ревью считаются в одном счётчике раундов фазы.

Шаг 5. Ревью фазы — всегда двойное, всегда Opus → Astra, кто бы ни писал код. Opus `high` (`review-spec.md`; `xhigh` если `risk: risky` или это последний раунд бюджета исполнителя) проверяет: закрыты ли критерии из `covers`, нет ли лишнего, соблюдён ли TDD. Затем Astra `high` (`review-quality.md`): баги, крайние случаи, читаемость. Вердикт ревьюера в `worker_done`: `PASS` или список замечаний с id и серьёзностью (`blocking`/`minor`). `blocking` → `fix-round.md` исполнителю; после фикса ревью начинается заново с Opus. `minor` без `blocking` считается PASS; минорные замечания попадают в коммит-сообщение как «не исправлено».

Бюджет фиксов фазы — одна конечная последовательность: (1) текущий исполнитель (Gemini, или Luna после фоллбэка по доступности) — до 3 раундов фиксов; (2) исчерпан, или исполнитель прислал `BLOCKED` по сложности — ровно одна эскалация: codex `gpt-6.1-sol` `high` в новом терминале (бриф `implementer.md` + последний отчёт и открытые замечания как контекст), свежий бюджет 3 раунда, старый терминал закрывается, в плане `implementer: sol`; (3) исчерпан бюджет Sol или `BLOCKED` от Sol → кап → одно сообщение пользователю (п. 4 правил). Фаза с `implementer: sol` (включая `hard: true`) эскалации не имеет: после 3 раундов сразу кап. Второй эскалации на Sol не бывает ни при каких условиях. Счётчик раундов живёт только в контексте сессии: при возобновлении фаза получает свежий бюджет 3 раунда с исполнителем из `implementer` — принятое упрощение (без ledger), а запрет второй эскалации держится на поле `implementer`.

Шаг 6. Коммит фазы координатором: сначала `status: done` фазе в плане, затем две отдельные команды `git add -A` и `git commit -m "<type>(<slug>): F<n> <title>"` (однострочное сообщение без `$`, обратных кавычек и переносов); закрыть терминалы исполнителя и ревьюеров (п. 9); `git status` чистый. Следующая фаза.

Шаг 7. Финальное ревью. Opus `high` (`final-review.md`, кап 2 раунда финального ревью): вся ветка против всех критериев спеки, итог — таблица «критерий → закрыт / не закрыт (почему)». Незакрытые критерии → координатор добавляет в план фазу `F<n+1>: final fixes` (`covers` = незакрытые критерии, `verify` = команды затронутых фаз, `risk` = максимум по ним) и прогоняет её шагами 4–6 целиком (исполнитель по ролям, `verify`, Opus → Astra, коммит); затем второй раунд финального ревью. Второй раунд с незакрытыми критериями → кап → вопрос пользователю. Все критерии закрыты, но есть строки `I<n> blocking` (проблемы интеграции) → один вопрос пользователю с этими строками и вариантами; завершение — только по `PASS`. Чистый итог → `status: done` плану, коммит `docs(<slug>): plan done`, отчёт пользователю: коммиты, результаты `verify`, таблица критериев, что осталось.

Правила:

- `gpt-6-luna` всегда `max`. `ultra` не используется. `roles.md` — выбор пользователя: нативное правило «`--model` только по просьбе» выполнено.
- Ревьюеры не подменяются другой моделью автоматически: порядок Opus → Astra фиксирован. Вопрос при недоступности ревьюера: «повторить позже / заменить на <другая модель из таблицы> только на этот раунд / стоп».
- Правило семейств осталось одно: спеку и план пишет Opus, ревьюит Astra. Для кода оно не применяется: Opus ревьюит и Opus-написанный фронтенд.
- Смена модели — всегда новый терминал (модель фиксируется при запуске). Фиксы — в терминале исполнителя.
- «Недоступен» — положительное свидетельство: `worker-start` упал или `spawn` вернул 3 (агент не запустился), `spawn` вернул 1 дважды подряд на свежих терминалах, `spawn` вернул 5 (неизвестная модалка) или 6 (экран входа), или `worker_done --outcome failed` с текстом про quota/rate limit/auth/launch. Для кодов 5 и 6 одно правило: если в строке роли есть альтернативная модель, не являющаяся упавшей (исполнитель Gemini → Luna; фронтенд Opus/Sonnet → agy), — объявленный переход на неё без повтора; иначе (авторы спеки/плана, Sol, все ревьюеры) — сразу один вопрос пользователю (повтор той же модели не делается: причина не временная). Код 6 — не сбой и не раунд фиксов. Возврат к основной модели — только при следующем независимом назначении (новая фаза или новая задача), не внутри текущей цепочки замен, и он не отменяет записанный `implementer: sol`/`luna` текущей фазы. Тишина недоступностью не считается (§«Сбои»).

## Правила координатора

1. Координатор не пишет код. Разрешённые записи: `orca_run`/`status`/`implementer`/фаза `final fixes` в frontmatter плана, git-операции (`add`, `commit`, `merge`, `merge --abort`, `rev-parse`, `status`, `diff`, `log`, `stash` только в шаге 0), и файлы для `--set-file` (отчёт ревью, замечания) в системной временной папке своей ОС (`$TMPDIR`/`/tmp` или `%TEMP%`) вне репозитория. Спеку, план, код и тесты пишут воркеры. Координатор читает код и запускает проверки. Каждая команда координатора — один вызов процесса без `$(...)`, `&&`, heredoc и пайпов; код выхода проверяется до следующей команды (`$?` в bash, `$LASTEXITCODE` в PowerShell); значения, полученные из вывода (SHA, handle, task_id), подставляются в следующую команду буквально. «Грязное дерево» везде в этой спеке означает `git status --porcelain` без строки `docs/plans/<slug>.md`: собственная правка frontmatter координатором деревом не считается и в вопросы пользователю не попадает.
2. Отчёт — текст `worker_done` (резюме, файлы, вердикт). Координатор проверяет сам: `git diff`, команды `verify`. Квитанций, ledger, хешей, `.superpowers/sdd/` нет. Бриф не пишется в файл: `orca_dev.py brief` заполняет шаблон в памяти и сам вызывает `task-create --spec <text>`; повторные dispatch'и в тот же терминал — `orca orchestration dispatch --task <id> --to <h> --inject --json`. Исход: каждый бриф велит `--outcome failed` только с subject `BLOCKED` (воркер не смог сделать работу), а любой другой отчёт, включая `FINDINGS` и строки «not fixed», — `--outcome succeeded`; вердикт определяет subject. Следующее ревью (спеки, плана, фазы) получает в токене `<PREVIOUS>` замечания прошлого раунда и строки автора `fixed` / `not fixed: <причина>` (до первого ревью — `—`).
3. Бриф с незаполненным плейсхолдером не уходит. Контракт `orca_dev.py brief` (см. таблицу подкоманд): шаблон может содержать угловые токены только вида `<UPPER_SNAKE>`; любой другой `<…>` в шаблоне (lint: `<absolute path>`, `<slug>`, кириллица) → код 1. После подстановки любой оставшийся `<UPPER_SNAKE>` → код 1, список токенов в stderr, Task не создаётся. Значения (`KEY=VALUE` и `--set-file KEY=<path>`) вставляются буквально и не сканируются (текст задачи может содержать HTML/JSX); файлы `--set-file` читаются как UTF-8, переносы строк сохраняются. Неизвестный `KEY` → код 2. Успех → код 0, `task_id` в stdout. Команды `worker_done`/`ask` в брифы не вписываются — воркер берёт их из нативного преамбула.
4. Капы: ревью спеки 3, ревью плана 4, финальное ревью 2, фиксы фазы — последовательность из шага 5 (3 у текущего исполнителя → одна эскалация на Sol с бюджетом 3 → кап). Достигнут → одно сообщение пользователю: открытые замечания + варианты «принять как есть / ещё раунд / стоп». «Ещё раунд» даёт ровно один дополнительный раунд у того же воркера, после него снова вопрос. HOLD не существует.
5. Сообщения пользователю только при смене состояния: триаж выбран; вопрос по спеке; спека готова к «ок»; план одобрен (сводка); фаза закоммичена (одна строка: id, заголовок, хеш); фоллбэк или эскалация; кап; BLOCKED-вопрос; финальный отчёт. Пока идёт ожидание воркера — молчание.
6. Триаж до любого dispatch'а (шаг 1).
7. Автокоммит фазы после чистого ревью; перед следующей фазой `git status` чистый. Пользователь может отключить автокоммит словами в задаче — тогда коммит заменяется строкой «готово к коммиту» и ожиданием.
8. Один Run на план (быстрый путь: один Run на задачу). Возобновление — `run-use --id <orca_run>` из frontmatter.
9. Терминалы. Координатор помнит handle каждого терминала, который создал в этом Run; все его терминалы называются `<slug>/<роль>-<фаза>` (`--title`). Две отдельные операции: *settle* Dispatch'а (делает Orca по `worker_done`) и *закрытие терминала* (делает координатор). Закрывать сразу после приёмки результата: ревьюера — после принятого отчёта; исполнителя — после коммита фазы или после замены (эскалация); автора спеки/плана — после одобрения. Команды: терминал, созданный `worker-start` (Path A) → `worker-release --dispatch <id> --json` (он и закрывает терминал; `retained` в ответе означает, что терминал не его — тогда `orca_dev.py close <h>`); терминал, созданный `spawn` (Path B) → `orca_dev.py close <h>` (на Path B `worker-release`/`worker-stop` процесс не трогают). `close` сам подтверждает закрытие (`result.close.ptyKilled: true` в receipt или отсутствие handle в `orca terminal list --worktree current --json`) и возвращает 1, если подтвердить не удалось. При старте/возобновлении: `worker-list --run <orca_run> --json` без фильтра состояния (Path B учитывается как `retained`, фильтр `reclaimable` их пропускает) → каждая строка с settled Task (`succeeded`/`failed`) и без живого Dispatch → её терминал закрыть; плюс строки `orca terminal list --worktree current --json` с title `<slug>/…`, не занятые живым Dispatch → закрыть. Чужие Run'ы, терминал координатора, терминалы без префикса `<slug>/` и открытые пользователем — не трогать. Неудавшееся закрытие не повторять: одна строка в финальном отчёте «терминал <h> не закрылся».

## Запуск воркеров (`launch.md`)

- Path B — единый путь для каждого свежего запуска любого агента, одной командой: `python3 <plugin>/bin/orca_dev.py spawn --agent <agy|codex|claude> --model <m> [--effort <e>] --title <slug>/<роль>-<фаза> --task <task_id>`. Внутри: `orca terminal create --worktree active --title <t> --command <argv> --json` → `orca terminal wait --terminal <h> --for tui-idle --timeout-ms 180000 --json` → `ready <h> <agent> <180|120|90 по агенту: agy|codex|claude>` (обязательно: `tui-idle` срабатывает на промпте оболочки, до отрисовки TUI агента) → `orca orchestration dispatch --task <task_id> --to <h> --inject --json`. Причины: Codex нужны `-c features.multi_agent=false` и bypass-флаги, которые `worker-start` не передаёт; свежий Claude через `worker-start` терял промпт в 3 из 6 запусков (смоук 2026-09-26); один рецепт для всех агентов проще трёх. `worker-start --model` для `antigravity` в Orca 1.4.224 документирован; если smoke покажет, что agy через Path A стартует надёжно, его можно разрешить для agy отдельной строкой в `launch.md` — не обязательно.
- Path A (`worker-start --task <id> --worktree current --agent <agent> --model <id> --effort <lvl>`) допускается для повторного использования живого терминала (`--terminal <h>`, без `--model/--effort`). Повторные dispatch'и в тот же терминал на Path B — `dispatch --task <next> --to <h> --inject`.
- argv, которые собирает `spawn` (записаны в `launch.md` как источник правды): Antigravity `agy --model gemini-3.8-flash-high --dangerously-skip-permissions` (без `--effort`); Codex `codex --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust -m <model> -c model_reasoning_effort=<lvl> -c features.multi_agent=false` (проверено на codex-cli 0.162.1); Claude `claude --dangerously-skip-permissions --model <opus|sonnet> --effort <lvl>`. Строку `--command` `spawn` собирает под ОС хоста (`shlex.join` на POSIX; на Windows — `subprocess.list2cmdline`), координатор её не набирает. Переменная `ORCA_STRIGOV_WORKER` упраздняется (хуков, от которых она освобождала, больше нет).
- `spawn` вернул 1 (агент не готов) → `close` терминала из `handle` и один повтор `spawn`; второй 1 подряд → «недоступен» → фоллбэк роли. Код 3 → «недоступен» сразу. Код 4 — не недоступность: терминал не закрывать, модель не менять, разбор по §«Сбои» («dispatch с неизвестным исходом»). Коды 5 и 6 → §«Сбои».
- Состояния старта харнеса (раздел «Старт агента» в `launch.md`):
  - Медленный старт. Пока на экране busy-маркер (`codex` «Starting MCP servers», `agy` «not signed in» в первые ~20 с — это гонка keyring, не логаут), `ready` ждёт молча. Таймауты по агенту: agy 180 с, codex 120 с, claude 90 с (`spawn` выбирает сам).
  - Модалки. Таблица «маркер на экране или `blockedReason` из `orca terminal wait` → действие»: Codex «Update available» (`codex-update-prompt`) → выбрать «пропустить»; «Hooks need review» (`codex-hooks-review-prompt`) → подтвердить; диалог доверия Claude и «Do you trust this folder?» Antigravity → подтвердить (репозиторий пользователя; `install.py --repo` и так их предотвращает). `spawn` снимает их сам через `orca terminal send` и продолжает ждать; точные клавиши для каждой строки таблицы фиксируются во время smoke по реальным экранам — таблица в 2.0.0 выходит с клавишами, проверенными при реализации. Неизвестная модалка (`agent_prompt_blocked`/`terminal send` отказан, маркер не из таблицы) → код 5 с фрагментом экрана.
  - Вход. Маркеры экранов входа в той же таблице: codex «Sign in with ChatGPT», claude «/login», agy «Select login method» дольше ~20 с → код 6. Команды для пользователя: `codex login`; `claude`, затем `/login`; `agy` и интерактивный вход.
  - Antigravity: одна строка в брифе исполнителя — не использовать таймер `Schedule` (он опрашивает модель каждые 30 с и сжигает квоту); ждать тест одним блокирующим вызовом shell.
- Осиротевшие терминалы: перед любым повторным dispatch'ем `orca terminal show --terminal <h> --json`; `orphaned: true` означает только «в этот терминал не отправлять» — не выход процесса. Settled воркер в нём → закрыть и открыть новый; не-settled писатель → правила молчания §«Сбои» (замена только после доказанного выхода).
- Ожидание: `orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 900000 --json`; `question` → `reply`; `worker_done` → приёмка → `check --ack <delivery_id>`.
- Риск: при смене флагов CLI Orca/Codex/agy `launch.md` правится руками; `install.py` проверяет `orca --version` и печатает его.
- Windows (раздел «Windows» в `launch.md`, ≤10 строк): координатор работает в PowerShell 5.1/7; хелпер вызывается `py -3 <plugin>\bin\orca_dev.py <подкоманда> …`; действует правило «одна команда — один вызов процесса, проверить `$LASTEXITCODE`» из п. 1 правил (поэтому `$(...)`, `&&`, `mktemp`, heredoc и экранирование кавычек не нужны — всё хрупкое делает `orca_dev.py`); `bash` не вызывать (может оказаться WSL-лаунчером); пути воркерам — абсолютные Windows-пути; `agy` на native Windows не проверен — если его нет на PATH, исполнитель стартует сразу с фоллбэка Luna с одной строкой пользователю.

## Сбои

- Воркер недоступен (определение в §«Роли») → колонка «Фоллбэк» таблицы ролей с одной строкой пользователю; там стоит «вопрос» → один вопрос с вариантами («повторить позже / заменить на <модель> только на этот раунд / стоп»).
- Молчит → `check --wait` (15 минут за вызов). После трёх пустых ожиданий подряд → `worker-list --run <orca_run> --json` и `worker-read --dispatch <id> --source auto`. Замена только при доказанном выходе процесса: `liveness: exited`, или транскрипт, где последний ход агента без `worker_done`, плюс `terminal show` без живого процесса → старый терминал закрыть, новый терминал той же роли с тем же брифом плюс строка «предыдущая попытка не завершилась; текущее состояние дерева — в `git status`». Если старый воркер — писатель (исполнитель, автор спеки/плана) и его выход не доказан (`unverifiable`, терминал жив) → не запускать замену; продолжать ждать, а после ещё трёх пустых ожиданий — один вопрос пользователю «ждать дальше / остановить и заменить / стоп». Ревьюера с недоказанным выходом можно заменить после шести пустых ожиданий без вопроса (он ничего не пишет). Пользователю во время ожидания не писать.
- Dispatch с неизвестным исходом (`spawn` код 4, `stage: dispatch`, `handle` есть): сначала `orca orchestration request-show --request <request_id> --json` и `orca orchestration dispatch-show --task <task_id> --json`. `completed` или Dispatch со статусом `pending`/`dispatched`/`completed` → задача доставлена: считать воркера работающим, ждать `check --wait`. `absent` и отсутствие Dispatch либо Dispatch со статусом `failed` (`last_failure` содержит ошибку отправки; Task снова `ready`) → один повтор того же запроса в тот же терминал с тем же `--retry-request` id: `orca orchestration dispatch --task <task_id> --to <handle> --inject --retry-request <request_id> --json`. Если после повтора Dispatch снова `failed` или исход `circuit_broken` → один вопрос пользователю. `pending` в `request-show`, противоречивые ответы или неизвестный исход повтора → терминал не трогать, ждать по правилам молчания выше, затем один вопрос пользователю («ждать дальше / остановить и заменить / стоп»). Новый писатель — только после доказанного выхода процесса этого терминала или по ответу пользователя на этот вопрос.
- `spawn` код 5 (неизвестная модалка) или 6 (экран входа): `close` терминала, затем правило из §«Роли»: есть альтернативная модель в строке роли → объявленный переход и ровно одна строка пользователю (код 5: «<агент> упёрся в неизвестный диалог: <фрагмент экрана>; работаю на <альтернатива>»; код 6: «<агент> разлогинен, работаю на <альтернатива>; чтобы вернуть — залогинься: <команда>»); альтернативы нет (авторы спеки/плана, Sol, ревьюеры) → один вопрос «повторить позже / заменить на <модель> только на этот раунд / стоп» с тем же фрагментом экрана или подсказкой про вход. В раунды фиксов это не считается; основная модель возвращается только при следующем независимом назначении.
- Кап → п. 4 правил.
- `BLOCKED` в отчёте исполнителя → если блокер о сложности/непонятном коде → единственная эскалация на Sol по шагу 5 (если исполнитель уже Sol или фаза `hard: true` → кап → вопрос); если блокер о требованиях (противоречие спеке, нужен выбор продукта) → один вопрос пользователю с вариантами, затем, если ответ меняет спеку, правка спеки тем же путём (Opus → Astra, кап 3) и продолжение той же фазы с тем же исполнителем (счётчик не сбрасывается).
- Простой `BLOCKED` (без уточнения `complexity`/`requirements`; так отчитываются, например, авторы спеки и плана) без признаков недоступности → один вопрос пользователю с причиной и вариантами продолжения; следующий шаг не начинать до ответа.
- `worker_done --outcome failed` с subject `DONE`, `PASS` или `FINDINGS` → вердикт определяет subject; любой другой `failed` без признаков недоступности → читать как BLOCKED.
- После рестарта Orca: алгоритм §«Состояние и возобновление»; `orphaned: true` у терминала трактуется по правилу выше (не отправлять, но и не считать процесс завершённым).

## Состояние и возобновление

Отдельной машины состояний нет. Состояние — frontmatter плана (`orca_run`, `status` плана и фаз) и git-история (коммиты фаз с `F<n>` в сообщении). Один алгоритм, на который ссылаются шаг 0, §«Сбои» и возобновление (пользователь называет план или slug):

1. `run-use --id <orca_run>`; закрыть отработавшие (settled) терминалы Run (п. 9).
2. Все фазы `done`, план `active` → шаг 7 (финальное ревью).
3. Первая фаза `pending` = F<n>. `worker-list --run <orca_run> --json` содержит не-settled Dispatch с title `<slug>/…-F<n>` → это живой писатель: ждать его через `check --wait` по правилам молчания §«Сбои»; новый исполнитель только после доказанного выхода старого (`liveness: exited` или собственное наблюдение выхода процесса). Дальше — после settle.
4. Дерево чистое и `git log --oneline -30` содержит коммит с префиксом `<type>(<slug>): F<n> ` (ровно тот, что даёт шаг 6) → поставить `done` (коммит `docs(<slug>): F<n> done`), вернуться к п. 2. Грязное дерево — сначала п. 5.
5. Дерево грязное → список файлов фазы: `git diff --name-only` без `docs/plans/<slug>.md` (метаданные координатора, в том числе незакоммиченный `implementer: sol`, не откатываются) плюс untracked из `git status --porcelain`, которые названы в плане/брифе фазы или в последнем отчёте исполнителя; остальные untracked в список не входят. Один вопрос с этим списком: «продолжить F<n> с текущими правками / откатить эти файлы: <список> (`git checkout -- <tracked>` и `rm` перечисленных untracked) / стоп». Если принадлежность файлов фазе неясна, список всё равно показывается, и решает пользователь. `git clean -fd` и stash не используются.
6. Иначе — F<n> с шага 4: исполнитель из `implementer` (поле пустое → по таблице ролей), свежий бюджет 3 раунда; `implementer: sol` → без эскалации. При «продолжить с правками» бриф получает строку «часть работы уже в дереве, см. `git diff`».

Быстрый путь не возобновляется: при обрыве задача запускается заново (грязное дерево → вопрос из шага 0).

## Установка

Актуальный контракт v2.1.0 (2026-10-22). Один исходник `skills/orca-dev/` содержит `SKILL.md`, `roles.md`, `launch.md`, `prompts/` (11 брифов), `scripts/orca_dev.py` и `scripts/install.py`. При сборке Codex добавляется `agents/openai.yaml`, при сборке Claude Code он отсутствует. В исходном репозитории удаляются `bin/`, корневой `install.py`, `plugin.json`, `.codex-plugin/` и `.claude-plugin/`. Единственный источник версии — `VERSION = "2.1.0"` в `scripts/install.py`. Этот состав заменяет плагинные строки исторической таблицы файлов выше.

Запуск из исходного checkout: `python3 skills/orca-dev/scripts/install.py …`, Windows: `py -3 skills/orca-dev/scripts/install.py …`. Из скачанной или установленной копии — её собственный `scripts/install.py`. Python 3.9+, стандартная библиотека; команды Orca передаются списками аргументов, без `shell=True`.

### Режимы и пути

| Режим | Действие |
|---|---|
| Без аргументов | Read-only проверки инструментов, штатных скиллов и старых копий. |
| `--agent claude` / `--agent codex` (повторяемый) | Подготовить вариант и скопировать его в каталог харнесса без runtime-проверок и trust-изменений. |
| `--repo PATH` (повторяемый) | Проверки и настройка доверия к репозиторию и его Git-worktree; с `--agent` сначала установка, затем trust и проверки. |
| `--check PATH` | Проверки и отчёт о доверии без записи; сочетание с `--agent` или `--bundle` — код 2 до любых записей. При совместном `--repo` сохраняется read-only поведение. |
| `--bundle DIR` | Только отдельно от других режимов: собрать обе папки и оба ZIP в отсутствующий или пустой DIR вне исходного скилла. |

Каталог Claude Code: `~/.claude/skills/orca-dev`. Каталог Codex: `$CODEX_HOME/skills/orca-dev`, если `CODEX_HOME` непустой, иначе `~/.codex/skills/orca-dev`. Установщик печатает разрешённый итоговый путь и не создаёт дополнительную копию в `~/.agents/skills`. Для домашнего каталога применяется `Path.home()`, на Windows — соответствующий профиль пользователя.

Пример установки обоих вариантов: `python3 skills/orca-dev/scripts/install.py --agent codex --agent claude`. Для работы координатора отдельно нужны Orca 1.4.224+, Git, вход в CLI моделей и штатные скиллы: `orca skills install --skill orchestration --skill orca-cli --agent codex,claude-code`.

### Renderer и обновление

Одна функция готовит вариант для установки и для ZIP, в том числе из уже подготовленного варианта другого харнесса. Перезаписываются frontmatter и абзац вызова: Codex — `$orca-dev` и `policy.allow_implicit_invocation: false` в `agents/openai.yaml`; Claude Code — `/orca-dev`, `disable-model-invocation: true` во frontmatter, без `context: fork` и Codex metadata. Общие модели, роли, брифы и правила процесса сохраняются; воркер не вызывает координаторский скилл.

Назначение распознаётся как наша standalone-установка только при наличии настоящего каталога (не симлинка), frontmatter `name: orca-dev`, файла `scripts/orca_dev.py` и отсутствии файлов вне разрешённого состава; `__pycache__` и `.DS_Store` при проверке состава игнорируются. Нераспознанная папка не изменяется. Это проверка структуры, а не доказательство неизменности содержимого: локальные правки внутри разрешённых файлов будут перезаписаны, о чём предупреждают README. Новая копия сначала готовится и проверяется в соседнем временном каталоге; прежняя сохраняется до успешной замены. Source == destination — no-op. Квитанции и постоянные журналы не создаются.

### Проверки окружения и trust

1. Проверка наличия штатных `orchestration` и `orca-cli`; отсутствие → WARN с командой установки и код 1. Эта проверка не блокирует самостоятельные `--agent` и `--bundle`.
2. Проверка версий Orca и CLI, готовности Orca, наличия `codex`, `claude`, `agy`, `git` на PATH; отсутствие `agy` в native Windows — INFO и предусмотренный fallback. Если доступна проверка обновлений, печатается подсказка; сами инструменты не обновляются.
3. `--repo` сохраняет существующую логику доверия: Claude Code — `~/.claude.json`, Antigravity — `~/.gemini/antigravity-cli/settings.json`, Codex — `~/.codex/config.toml`. Учитываются Git-worktree и платформенные пути; JSON записывается атомарно, существующие конфликтующие TOML-таблицы не перезаписываются. Отсутствующий конфиг → подсказка запустить соответствующий CLI. `--check` ничего не записывает.
4. Старые копии ищутся в `.claude/skills`, `.codex/skills`, `.agents/skills` и `$CODEX_HOME/skills` при его наличии. Обе распознанные standalone-копии с текущей `VERSION` считаются актуальными; версия читается как текст, код копии не исполняется. Старый `~/.codex/plugins/cache/personal/orca-strigov` перечисляется целиком. Для vendored `orchestration`/`orca-cli` проверяется компонент `orca-strigov` в разрешённом пути, а не произвольная подстрока. Проверки ничего не удаляют.

Коды выхода: 0 — успех без предупреждений, 1 — предупреждение или ошибка операции, 2 — некорректное использование. При сочетании `--agent` и `--repo` установка может завершиться до предупреждения на этапе trust; README рекомендует отдельные шаги.

### Релиз и снятие старого плагина

`--bundle DIR` создаёт `DIR/claude/orca-dev/`, `DIR/codex/orca-dev/`, `DIR/orca-dev-claude-v2.1.0.zip` и `DIR/orca-dev-codex-v2.1.0.zip`. У ZIP один верхний каталог `orca-dev/`, явный список файлов, отсортированные entries и фиксированные timestamps; `__pycache__`, `.pyc`, `.DS_Store` и результаты прошлых сборок не включаются.

Ветка `release` формируется из принятого коммита main в отдельной временной рабочей копии, содержит только оба варианта и краткий README с исходным SHA. Оба ZIP должны совпадать с файлами этой ветки. Тег `v2.1.0` ставится на исходный коммит main. После первого создания ветка обновляется обычными коммитами без переписывания истории; v2.0.0 и его asset сохраняются.

Миграция пользовательской установки выполняется отдельно от установщика: подготовить и проверить standalone-копии; завершить активную координаторскую работу; выполнить штатный `codex plugin remove orca-strigov@personal`; проверить результат; удалить только подтверждённые оставшиеся записи и копии этого плагина, сохраняя соседние плагины и исходные checkout. Затем новая сессия и проверка единственного актуального скилла. Проверка файлов не заменяет проверку загрузки в харнесс.

Оба README описывают самостоятельную установку, команды обоих харнессов, готовые архивы и ветку `release`, ограничения обновления, роли и ссылку на эту спецификацию. Лимит — 200 строк на язык; AGENTS.md — 30 строк.

## Проверка

1. `python3 -m unittest discover tests` (на Windows `py -3 -m unittest discover tests`), без Orca, один файл `tests/test_orca_dev.py`:
   - `brief --dry-run`: успешная подстановка; шаблон с `<absolute path>` / `<slug>` / `<путь>` → код 1 (lint шаблона); незаполненный `<REPORT>` → код 1; значение `<div>text</div>` подставляется буквально и проходит; `--set-file` с многострочным UTF-8 (кириллица, пустые строки, CRLF на входе) доходит до вывода без потерь; неизвестный ключ → код 2; при ненулевом коде `task-create` не вызывается (проверяется подменой функции запуска `orca`);
   - `ready`, только чистые функции: экран с «Ask Codex» и «Starting MCP servers» → не готов; без busy-строки → готов; «Antigravity» + «not signed in» → не готов; маркер в scrollback выше последних 25 строк stream-чтения не засчитывается; произвольный маркер ищется буквально; экран с «Update available» → известная модалка `codex-update-prompt`; экран с «Sign in with ChatGPT» / «/login» / «Select login method» (после порога) → `needs_login`; незнакомый вопрос с `blockedReason` не из таблицы → `blocked`;
   - `spawn` с подменённым запуском `orca`: экран «Update available», после отправки клавиш — «Ask Codex» → код 0, JSON `dismissed: ["codex-update-prompt"]`; экран входа Codex → код 6, `agent: "codex"`, `handle` заполнен; незнакомая модалка → код 5 с `screen`;
   - `spawn`, сборка argv: три агента дают ровно строки из `launch.md`; `agy` без `--effort`; строка `--command` для POSIX и Windows собирается без shell;
   - `spawn`, частичный сбой с подменённым запуском `orca`: `terminal create` отвечает handle, `terminal wait` и `ready` проходят, `dispatch` возвращает ошибку → код 4, JSON содержит `stage: "dispatch"`, этот `handle`, `task_id`, `request_id` и текст ошибки, `dispatch_id: null`; отказ на `terminal create` → код 3, `handle: null`.
2. Smoke-прогон в Orca на игрушечной задаче (временный git-репозиторий с одним Python-скриптом во временной папке ОС, создаётся пользователем/реализатором до запуска координатора):
   - быстрый путь: «добавь флаг `--version`» → старты agy Flash, Opus `high`, Astra `high` (сверка `launch.effective` в receipt или строки модели на экране `orca terminal read --screen`), один коммит, три терминала закрыты и отсутствуют в `orca terminal list --worktree current --json`, `docs/` не появился;
   - полный путь: «добавь подкоманду `stats` с тестами» → спека с AC, «ок» пользователя, план с frontmatter, ≥1 фаза, коммиты `docs:` и `F1`, финальная таблица критериев, `worker-list --run <orca_run> --json` не содержит строк с живым терминалом, `terminal list` не содержит title `<slug>/…`.
3. Оба прогона выполняются на macOS из Codex-координатора и повторяются из Claude Code-координатора хотя бы для быстрого пути.
4. Windows: юнит-тесты п. 1 и быстрый путь один раз из Windows-координатора (Codex или Claude Code) в Orca. Нет Windows-машины в момент реализации → в финальном отчёте строка «Windows: юнит-тесты и smoke не прогнаны»; завершение не блокируется.

### Дополнительная проверка поставки v2.1.0

- Перенесённые unit-тесты выполняются на Python 3.9 и основном Python без работающей Orca. Проверяются renderer обоих харнессов, повторный рендер и установка из готового варианта другого харнесса.
- Каждый ZIP распаковывается во временный каталог, не связанный с checkout; из постороннего CWD проверяются helper `--help`, поиск и заполнение брифов с fake Orca, все относительные ссылки в поставке. Плагинные манифесты и пути не требуются.
- Проверяются установка обоих харнессов и повторная установка, no-op при source == destination, отказ для чужого каталога и симлинка, сохранение прежней установки при сбое подготовки/замены.
- Оба актуальных варианта исключены из stale; старый кэш плагина обнаруживается; штатные скиллы сохраняются. Режимы только `--agent`/`--bundle` не вызывают runtime-проверки и не меняют trust, `--check` и отклонённые комбинации не пишут.
- Две сборки из одного исходника дают одинаковые ZIP; распакованные файлы совпадают с release tree. Публикуемые версии и исходный SHA сверены.
- В новых сессиях Codex и Claude Code проверяются обнаружение единственного актуального скилла, правильный вызов и политика запрета неявного запуска. Без реального наблюдения результат — `NOT_RUN`; упаковочные тесты не подтверждают выполнение полного пайплайна.

Результаты smoke фиксируются в сообщении пользователю, не в файлах репозитория.

## Риски

| Риск | Что делаем |
|---|---|
| Orca/Codex/agy меняют флаги CLI | `launch.md` и argv-таблица в `orca_dev.py spawn` правятся руками в одном месте; `install.py` печатает версии; `ready` ищет маркеры на экране, а не в потоке |
| Клавиши и тексты модалок/экранов входа меняются с версиями CLI | Таблица в `launch.md` — единственное место; клавиши фиксируются по реальным экранам в smoke; незнакомая модалка не вешает пайплайн (код 5 → фоллбэк или вопрос); `install.py` предупреждает о доступном обновлении |
| Нативный гайд меняет формулировки (классификатор ролей, `--model`) | Конфликты сняты явными строками в `SKILL.md`; при `orca skills update` перечитать три строки таблицы в §«Архитектура» |
| Без C6 ревьюер той же семьи, что автор кода | Принято сознательно: двойное ревью Opus → Astra покрывает обе семьи на каждой фазе; для спеки/плана пара Opus/Astra сохранена |
| Координатор снова начнёт «ждать доказательств» | Правила 2, 4, 5 и §«Сбои» дают выход из каждой ветки; слова HOLD в скилле нет (AC7) |
| Path B-терминалы копятся (release их не закрывает) | Правило 9: явный `terminal close` с подтверждением; чистка по `worker-list` без фильтра и по префиксу title при старте |
| Флаги `--dangerously-*` у воркеров | Как в 1.1.0; trust репозитория через `install.py --repo` снимает только диалоги доверия, не песочницу |
| Стейл-копии скиллов в кэше Codex подхватываются вместо новых | `install.py` предупреждает; координатор при первом запуске спрашивает разрешение на удаление |
| Windows не проверен в момент реализации (нет машины, `agy` на Windows не проверен) | Один исходник на Python 3.10+ без платформенных веток кроме путей, `shutil.which` и сборки `--command`; shell координатора не несёт ничего хрупкого (п. 1 правил); при отсутствии машины юнит-тесты и smoke на Windows отмечаются «не прогнаны» и не блокируют |
