# orca-dev v2 («orca-dev-lite»): спека дизайна

Дата: 2026-10-14. Репозиторий: `/Users/strigov/Documents/Claude/Projects/projects-code/orca-strigov`. Версия плагина после реализации: 2.0.0.

## Почему

Плагин 1.1.0 ломается на простых задачах. Последний случай (репозиторий Bureau): слияние двух уже принятых, бесконфликтных веток простояло больше часа в C6 `HOLD H1` (ждали доказательств семейства модели между Run'ами), породило 224 файла артефактов на 116 МБ, брифы ушли воркерам с незаполненными `<…>`, а координатор каждые ~90 с печатал одну и ту же строку статуса.

Причина структурная: плагин дублирует жизненный цикл Orca собственной машиной состояний (`bin/lib/protocol_state.py` + `protocol_facts.py`, ~1700 строк), квитанциями, ledger'ом, хешами и хуками, которые запрещают координатору завершать ход. Каждая проверка может уйти в HOLD, и ни одна не имеет выхода «сделать по-простому».

Orca 1.4.224 (`/Applications/Orca.app/Contents/Resources/bin/orca`) уже умеет всё нужное: `orca orchestration` (run-create/run-use, task-create, worker-start, dispatch --inject, check --wait, ask/reply, worker-list/show/read/stop/release) и штатные скиллы `orchestration` и `orca-cli` (`orca skills install`, `orca skills get`, `orca skills update`). Плагин должен быть тонким слоем над ними: пайплайн, пресеты моделей, рецепты запуска. Ничего больше.

## Цели и вне скоупа

Цели:

1. Разработка по SDD: спека с проверяемыми критериями приёмки (стиль Kiro) → план по фазам → TDD-исполнение → двойное ревью каждой фазы → финальное ревью ветки (цепочка Superpowers).
2. Ни одной ситуации без выхода: любой кап или сбой заканчивается объявленным фоллбэком или одним вопросом пользователю с вариантами.
3. Один `SKILL.md`, который работает координатором и в Codex, и в Claude Code.
4. Жизненный цикл воркеров целиком у нативного гайда Orca; наш код — только `wait-agent-ready` и `prompt-fill`.
5. Экономия диска: работа в текущем checkout, без новых worktree и служебных папок.

Вне скоупа:

- Windows (native PowerShell). `.ps1`-порты и `recipes-windows.md` удаляются: `prompt-fill` переписывается с новым контрактом, и порт пришлось бы писать заново и проверять на Windows-хосте. Git-история хранит старые порты.
- Параллельные фазы в worktree, бридж `chatgpt-web/pro`, профили планирования, роли gate/synthesizer/diagnosis/quickfix/integration-check.
- Публикация в marketplace (release-скрипты и workflows удаляются; плагин ставится из checkout как personal plugin).
- Автоматическая чистка кэша плагинов Codex и `.superpowers/` в целевых репозиториях (только предупреждение и вопрос).

## Критерии приёмки плагина

- AC1. КОГДА координатор получает `$orca-dev <задача>` (Codex) или `/orca-strigov:orca-dev <задача>` (Claude Code), ТОГДА он первым делом выполняет `orca skills get orchestration`, затем `run-create` (или `run-use` для возобновления), и ни одна команда плагина не создаёт файлов внутри целевого репозитория кроме `docs/specs/*.md`, `docs/plans/*.md` и правок кода воркерами.
- AC2. КОГДА задача проходит триаж как быстрый путь, ТОГДА пайплайн идёт «исполнитель → проверки координатором → ревью Opus → ревью Astra → коммит» без спеки и плана, и в `docs/` не появляется новых файлов; для слияния уже принятых веток слияния выполняет сам координатор, а проверки и ревью покрывают диапазон `"$BASE"..HEAD`.
- AC3. КОГДА задача идёт полным путём, ТОГДА спеку `docs/specs/<YYYY-MM-DD>-<slug>.md` пишет воркер Opus, ревьюит Astra (не более 3 раундов), и работа над планом не начинается, пока пользователь не ответил «ок» на спеку.
- AC4. КОГДА спека одобрена, ТОГДА план `docs/plans/<slug>.md` с frontmatter из §«План» пишет Opus `xhigh`, ревьюит Astra `xhigh` (не более 4 раундов), координатор коммитит спеку+план одним коммитом и переходит к первой фазе без ожидания пользователя (если пользователь не просил показать план).
- AC5. КОГДА исполнитель прислал `worker_done` по фазе, ТОГДА координатор сам выполняет `git diff` и каждую команду из `verify:` фазы, и при красном результате возвращает замечания тому же исполнителю в тот же терминал.
- AC6. КОГДА проверки фазы зелёные, ТОГДА ревью идёт в порядке Opus (соответствие спеке) → Astra (качество кода), после чистого ревью координатор коммитит фазу, ставит `status: done` в плане и закрывает терминалы фазы.
- AC7. КОГДА кап достигнут (ревью спеки 3; плана 4; финального ревью 2; фиксы фазы — 3 раунда у текущего исполнителя, затем единственная эскалация на Sol с новым бюджетом 3, затем кап), ТОГДА координатор отправляет пользователю одно сообщение с открытыми замечаниями и вариантами «принять как есть / ещё раунд / стоп» и ждёт ответа; второй эскалации на Sol не бывает; слов `HOLD` и `UNVERIFIABLE` в сообщениях пользователю нет.
- AC8. КОГДА основная модель роли недоступна, ТОГДА координатор действует по колонке «Фоллбэк» таблицы ролей (объявленный фоллбэк для авторов и исполнителей; для ревьюеров — один повтор той же модели в новом терминале, затем вопрос) и сообщает об этом одной строкой.
- AC9. КОГДА `prompt-fill` получает шаблон, в котором есть угловой токен не вида `<UPPER_SNAKE>` или после подстановки остался незаполненный `<UPPER_SNAKE>`, ТОГДА он завершается с кодом 1, печатает список токенов и не пишет файл; подставленные значения вставляются буквально и не проверяются.
- AC10. КОГДА координатор принял результат воркера (отчёт ревьюера, коммит фазы, одобрение спеки/плана), ТОГДА терминал этого воркера закрыт и закрытие подтверждено (`ptyKilled: true` или отсутствие в `orca terminal list`) до следующего шага пайплайна; при старте и возобновлении закрыты все отработавшие терминалы своего Run, включая Path B (состояние `retained`).
- AC11. КОГДА сессия координатора возобновляется, ТОГДА он восстанавливает состояние по алгоритму §«Состояние и возобновление» из `orca_run`, `status` и `implementer` фаз в плане плюс `git log` и `worker-list --run`, без иных файлов состояния, и не запускает нового исполнителя фазы, пока у неё есть не-settled Dispatch.
- AC12. КОГДА пользователь ничего не спрашивает, ТОГДА координатор пишет ему только при смене состояния (список в §«Правила координатора»); повторных строк статуса по таймеру нет.
- AC13. КОГДА `install.sh` запущен без штатно установленных `orchestration` и `orca-cli`, ТОГДА он печатает команду `orca skills install --skill orchestration --skill orca-cli --agent codex,claude-code` и завершается с кодом 1; с `--repo <path>` он выдаёт trust репозиторию для Claude и Antigravity как в 1.1.0.
- AC14. КОГДА плагин 2.0.0 установлен, ТОГДА в нём нет `hooks/`, `bin/lib/protocol_*`, `contracts/`, вендоренных `skills/orchestration` и `skills/orca-cli`, и smoke-прогон в Orca (§«Проверка») проходит по быстрому и полному пути.

## Пайплайн

Шаг 0. Старт. `orca skills get orchestration`; `orca status --json` (runtime `ready`); `run-create --objective "<slug или задача>"` или `run-use --id <orca_run>` при возобновлении; закрыть отработавшие терминалы своего Run (§«Правила координатора» п. 9). Новая задача (плана ещё нет) при грязном `git status` → один вопрос «закоммитить как есть / отложить (`git stash`) / стоп» — это единственное место, где stash допустим. Возобновление — по алгоритму §«Состояние и возобновление».

Шаг 1. Триаж. Быстрый путь, если выполняются все условия: ≤2 файлов кода по оценке координатора, нет изменений схем/миграций/безопасности/публичных API. Сюда же входит слияние уже принятых веток. Иначе полный путь. Решение сообщается пользователю одной строкой вместе с первым dispatch'ем.

Быстрый путь: исполнитель (бриф `implementer.md`, роль «Исполнитель») → `worker_done` → координатор: `git diff` + проверки, которые сам назначил в брифе (тесты/линт проекта) → ревью Opus (`review-spec.md`, критерий — формулировка задачи) → ревью Astra (`review-quality.md`) → коммит → закрыть терминалы → итог пользователю. Фиксы и капы как у фазы (шаги 4–5).

Подпуть «слияние уже принятых веток»: координатор сам (git-операции ему разрешены) записывает `BASE=$(git rev-parse HEAD)` и выполняет `git merge --no-ff <ref>` для каждой ветки по порядку. Конфликт → `git merge --abort` этой ветки, и её слияние с разрешением конфликтов уходит исполнителю как обычная задача быстрого пути (исполнитель коммитит merge-коммит сам). После всех слияний: проверки проекта, ревью Opus → Astra по `git diff "$BASE"..HEAD` (список коммитов — `git log --oneline "$BASE"..HEAD`); `blocking` → фиксы исполнителем дополнительными коммитами, повторное ревью; если ревью чистое и фиксов не было — дополнительных коммитов нет, итог пользователю со списком merge-коммитов.

Шаг 2. Спека (полный путь). Координатор сам ведёт короткий диалог с пользователем: по одному вопросу за сообщение, только то, без чего спеку не написать (обычно 1–3 вопроса). Затем бриф `spec-writer.md` → Opus `xhigh` пишет `docs/specs/<YYYY-MM-DD>-<slug>.md` с разделами: Цель; Вне скоупа; Критерии приёмки — пронумерованные `AC1…`, каждый в форме «КОГДА <условие>, ТОГДА <наблюдаемый результат>»; Дизайн (архитектура, файлы, интерфейсы). Astra `xhigh` ревьюит (`spec-review.md`): замечания списком с id; правит тот же Opus в своём терминале на `high` (`spec-revise.md`); кап 3 раунда. Чистое ревью → координатор показывает пользователю ссылку на файл и критерии приёмки и ждёт «ок». Это единственная обязательная остановка.

Шаг 3. План. Бриф `plan-writer.md` → Opus `xhigh` пишет `docs/plans/<slug>.md`:

```yaml
---
spec: docs/specs/2026-10-14-<slug>.md
orca_run: run_xxxxxxxxxxxx      # вписывает координатор перед dispatch'ем
status: active                  # active | done — ставит координатор
phases:
  - id: F1
    title: Хранилище
    risk: none                  # none | risky — risky: безопасность, данные, миграции, конкурентность
    area: backend               # backend | frontend
    hard: false                 # true — автор плана считает фазу заведомо сложной → исполнитель Sol с самого начала
    implementer: gemini         # gemini | luna | sol | opus | sonnet — текущий исполнитель; ставит координатор при запуске, фоллбэке и эскалации
    covers: [AC1, AC2]
    verify:
      - pytest tests/test_storage.py -q
      - ruff check src/
    status: pending             # pending | done — ставит координатор
---
```

Тело: по одному `## F<n>: <title>` на фазу — что сделать, какие файлы, какие тесты написать первыми, что закрывает. Каждый критерий спеки покрыт хотя бы одной фазой; фаза без `covers` недопустима. Обычно 1–5 фаз. Автор плана `implementer` не заполняет; координатор вписывает его при запуске исполнителя фазы (`gemini`, или `sol` для `hard: true`, или `opus`/`sonnet` для `area: frontend`) и меняет при фоллбэке/эскалации. Между коммитами фаз эта правка plan-файла остаётся незакоммиченной и попадает в коммит фазы. Astra `xhigh` ревьюит (`plan-review.md`, кап 4); правит тот же Opus на `high` (`plan-revise.md`). После чистого ревью координатор вписывает `orca_run`, коммитит спеку и план (`docs: spec + plan for <slug>`) и идёт к фазе F1; пользователю — краткая сводка (число фаз, их названия). Если пользователь заранее просил показать план — остановка на «ок».

Шаг 4. Фаза. Бриф `implementer.md` (в нём: путь к спеке и плану, id фазы, её `covers`, `verify`, требование TDD: сначала тест на критерий, потом код; запрет трогать файлы вне фазы без упоминания в отчёте). После `worker_done` координатор: `git diff --stat`, затем каждая команда `verify`. Красное или ошибки в отчёте → `fix-round.md` тому же исполнителю в тот же терминал (`dispatch --inject`). Технические фиксы и фиксы по ревью считаются в одном счётчике раундов фазы.

Шаг 5. Ревью фазы — всегда двойное, всегда Opus → Astra, кто бы ни писал код. Opus `high` (`review-spec.md`; `xhigh` если `risk: risky` или это последний раунд бюджета исполнителя) проверяет: закрыты ли критерии из `covers`, нет ли лишнего, соблюдён ли TDD. Затем Astra `high` (`review-quality.md`): баги, крайние случаи, читаемость. Вердикт ревьюера в `worker_done`: `PASS` или список замечаний с id и серьёзностью (`blocking`/`minor`). `blocking` → `fix-round.md` исполнителю; после фикса ревью начинается заново с Opus. `minor` без `blocking` считается PASS; минорные замечания попадают в коммит-сообщение как «не исправлено».

Бюджет фиксов фазы — одна конечная последовательность: (1) текущий исполнитель (Gemini, или Luna после фоллбэка по доступности) — до 3 раундов фиксов; (2) исчерпан, или исполнитель прислал `BLOCKED` по сложности — ровно одна эскалация: codex `gpt-6.1-sol` `high` в новом терминале (бриф `implementer.md` + последний отчёт и открытые замечания как контекст), свежий бюджет 3 раунда, старый терминал закрывается, в плане `implementer: sol`; (3) исчерпан бюджет Sol или `BLOCKED` от Sol → кап → одно сообщение пользователю (п. 4 правил). Фаза с `implementer: sol` (включая `hard: true`) эскалации не имеет: после 3 раундов сразу кап. Второй эскалации на Sol не бывает ни при каких условиях. Счётчик раундов живёт только в контексте сессии: при возобновлении фаза получает свежий бюджет 3 раунда с исполнителем из `implementer` — принятое упрощение (без ledger), а запрет второй эскалации держится на поле `implementer`.

Шаг 6. Коммит фазы координатором: `git add -A && git commit -m "<type>(<slug>): F<n> <title>"`; `status: done` фазе в плане (в том же коммите); закрыть терминалы исполнителя и ревьюеров (п. 9); `git status` чистый. Следующая фаза.

Шаг 7. Финальное ревью. Opus `high` (`final-review.md`, кап 2 раунда финального ревью): вся ветка против всех критериев спеки, итог — таблица «критерий → закрыт / не закрыт (почему)». Незакрытые критерии → координатор добавляет в план фазу `F<n+1>: final fixes` (`covers` = незакрытые критерии, `verify` = команды затронутых фаз, `risk` = максимум по ним) и прогоняет её шагами 4–6 целиком (исполнитель по ролям, `verify`, Opus → Astra, коммит); затем второй раунд финального ревью. Второй раунд с незакрытыми критериями → кап → вопрос пользователю. Чистый итог → `status: done` плану, коммит `docs(<slug>): plan done`, отчёт пользователю: коммиты, результаты `verify`, таблица критериев, что осталось.

Правила:

- `gpt-6-luna` всегда `max`. `ultra` не используется. `roles.md` — выбор пользователя: нативное правило «`--model` только по просьбе» выполнено.
- Ревьюеры не подменяются другой моделью автоматически: порядок Opus → Astra фиксирован. Вопрос при недоступности ревьюера: «повторить позже / заменить на <другая модель из таблицы> только на этот раунд / стоп».
- Правило семейств осталось одно: спеку и план пишет Opus, ревьюит Astra. Для кода оно не применяется: Opus ревьюит и Opus-написанный фронтенд.
- Смена модели — всегда новый терминал (модель фиксируется при запуске). Фиксы — в терминале исполнителя.
- «Недоступен» — положительное свидетельство: `worker-start`/`terminal create` упал, `wait-agent-ready` вернул 1 дважды подряд на свежих терминалах, или `worker_done --outcome failed` с текстом про quota/rate limit/auth/launch. Тишина недоступностью не считается (§«Сбои»).

## Правила координатора

1. Координатор не пишет код. Разрешённые записи: `orca_run`/`status`/`implementer`/фаза `final fixes` в frontmatter плана, git-операции (`add`, `commit`, `merge`, `merge --abort`, `status`, `diff`, `log`, `stash` только в шаге 0), брифы во временной папке (`mktemp -d`) вне репозитория. Спеку, план, код и тесты пишут воркеры. Координатор читает код и запускает проверки. «Грязное дерево» везде в этой спеке означает `git status --porcelain` без строки `docs/plans/<slug>.md`: собственная правка frontmatter координатором деревом не считается и в вопросы пользователю не попадает.
2. Отчёт — текст `worker_done` (резюме, файлы, вердикт). Координатор проверяет сам: `git diff`, команды `verify`. Квитанций, ledger, хешей, `.superpowers/sdd/` нет. Брифы уходят прямо в `task-create --spec "$(cat <brief>)"` / `worker-start --spec` / `dispatch`.
3. Бриф с незаполненным плейсхолдером не уходит. Контракт `prompt-fill`: `prompt-fill <template.md> --out <file> KEY=VALUE ...`. Шаблон может содержать угловые токены только вида `<UPPER_SNAKE>`; любой другой `<…>` в шаблоне (lint: `<absolute path>`, `<slug>`, кириллица) → код 1. После подстановки любой оставшийся `<UPPER_SNAKE>` → код 1, список токенов в stderr, файл не создан. Значения вставляются буквально и не сканируются (текст задачи может содержать HTML/JSX). Неизвестный `KEY` или существующий `--out` → код 2. Успех → код 0, путь в stdout. Команды `worker_done`/`ask` в брифы не вписываются — воркер берёт их из нативного преамбула.
4. Капы: ревью спеки 3, ревью плана 4, финальное ревью 2, фиксы фазы — последовательность из шага 5 (3 у текущего исполнителя → одна эскалация на Sol с бюджетом 3 → кап). Достигнут → одно сообщение пользователю: открытые замечания + варианты «принять как есть / ещё раунд / стоп». «Ещё раунд» даёт ровно один дополнительный раунд у того же воркера, после него снова вопрос. HOLD не существует.
5. Сообщения пользователю только при смене состояния: триаж выбран; вопрос по спеке; спека готова к «ок»; план одобрен (сводка); фаза закоммичена (одна строка: id, заголовок, хеш); фоллбэк или эскалация; кап; BLOCKED-вопрос; финальный отчёт. Пока идёт ожидание воркера — молчание.
6. Триаж до любого dispatch'а (шаг 1).
7. Автокоммит фазы после чистого ревью; перед следующей фазой `git status` чистый. Пользователь может отключить автокоммит словами в задаче — тогда коммит заменяется строкой «готово к коммиту» и ожиданием.
8. Один Run на план (быстрый путь: один Run на задачу). Возобновление — `run-use --id <orca_run>` из frontmatter.
9. Терминалы. Координатор помнит handle каждого терминала, который создал в этом Run; все его терминалы называются `<slug>/<роль>-<фаза>` (`--title`). Две отдельные операции: *settle* Dispatch'а (делает Orca по `worker_done`) и *закрытие терминала* (делает координатор). Закрывать сразу после приёмки результата: ревьюера — после принятого отчёта; исполнителя — после коммита фазы или после замены (эскалация); автора спеки/плана — после одобрения. Команды: терминал, созданный `worker-start` (Path A) → `worker-release --dispatch <id> --json` (он и закрывает терминал; `retained` в ответе означает, что терминал не его — тогда `terminal close`); терминал, созданный `terminal create` (Path B) → `orca terminal close --terminal <h> --json` (на Path B `worker-release`/`worker-stop` процесс не трогают). Подтверждение закрытия: `result.close.ptyKilled: true` в receipt или отсутствие handle в `orca terminal list --worktree current --json`. При старте/возобновлении: `worker-list --run <orca_run> --json` без фильтра состояния (Path B учитывается как `retained`, фильтр `reclaimable` их пропускает) → каждая строка с settled Task (`succeeded`/`failed`) и без живого Dispatch → её терминал закрыть; плюс строки `orca terminal list --worktree current --json` с title `<slug>/…`, не занятые живым Dispatch → закрыть. Чужие Run'ы, терминал координатора, терминалы без префикса `<slug>/` и открытые пользователем — не трогать. Неудавшееся закрытие не повторять: одна строка в финальном отчёте «терминал <h> не закрылся».

## Запуск воркеров (`launch.md`)

- Path B — единый путь для каждого свежего запуска любого агента: `orca terminal create --worktree active --title "<slug>/<роль>-<фаза>" --command "<argv>" --json` → `orca terminal wait --terminal <h> --for tui-idle --timeout-ms 180000 --json` → `bin/wait-agent-ready <h> <agy|codex|claude> 120` (обязательно: `tui-idle` срабатывает на промпте оболочки, до отрисовки TUI агента) → `orca orchestration dispatch --task <task_id> --to <h> --inject --json`. Причины: Codex нужны `-c features.multi_agent=false` и bypass-флаги, которые `worker-start` не передаёт; свежий Claude через `worker-start` терял промпт в 3 из 6 запусков (смоук 2026-09-26); один рецепт для всех агентов проще трёх. `worker-start --model` для `antigravity` в Orca 1.4.224 документирован; если smoke покажет, что agy через Path A стартует надёжно, его можно разрешить для agy отдельной строкой в `launch.md` — не обязательно.
- Path A (`worker-start --task <id> --worktree current --agent <agent> --model <id> --effort <lvl>`) допускается для повторного использования живого терминала (`--terminal <h>`, без `--model/--effort`). Повторные dispatch'и в тот же терминал на Path B — `dispatch --task <next> --to <h> --inject`.
- argv: Antigravity `agy --model gemini-3.8-flash-high --dangerously-skip-permissions` (без `--effort`); Codex `codex --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust -m <model> -c model_reasoning_effort=<lvl> -c features.multi_agent=false` (проверено на codex-cli 0.162.1); Claude `claude --dangerously-skip-permissions --model <opus|sonnet> --effort <lvl>`. Переменная `ORCA_STRIGOV_WORKER` упраздняется (хуков, от которых она освобождала, больше нет).
- `wait-agent-ready` вернул 1 → один повтор в новом терминале (старый закрыть); второй 1 подряд → «недоступен» → фоллбэк роли.
- Осиротевшие терминалы: перед любым повторным dispatch'ем `orca terminal show --terminal <h> --json`; `orphaned: true` означает только «в этот терминал не отправлять» — не выход процесса. Settled воркер в нём → закрыть и открыть новый; не-settled писатель → правила молчания §«Сбои» (замена только после доказанного выхода).
- Ожидание: `orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 900000 --json`; `question` → `reply`; `worker_done` → приёмка → `check --ack <delivery_id>`.
- Риск: при смене флагов CLI Orca/Codex/agy `launch.md` правится руками; `install.sh` проверяет `orca --version` и печатает его.

## Сбои

- Воркер недоступен (определение в §«Роли») → колонка «Фоллбэк» таблицы ролей с одной строкой пользователю; там стоит «вопрос» → один вопрос с вариантами («повторить позже / заменить на <модель> только на этот раунд / стоп»).
- Молчит → `check --wait` (15 минут за вызов). После трёх пустых ожиданий подряд → `worker-list --run <orca_run> --json` и `worker-read --dispatch <id> --source auto`. Замена только при доказанном выходе процесса: `liveness: exited`, или транскрипт, где последний ход агента без `worker_done`, плюс `terminal show` без живого процесса → старый терминал закрыть, новый терминал той же роли с тем же брифом плюс строка «предыдущая попытка не завершилась; текущее состояние дерева — в `git status`». Если старый воркер — писатель (исполнитель, автор спеки/плана) и его выход не доказан (`unverifiable`, терминал жив) → не запускать замену; продолжать ждать, а после ещё трёх пустых ожиданий — один вопрос пользователю «ждать дальше / остановить и заменить / стоп». Ревьюера с недоказанным выходом можно заменить после шести пустых ожиданий без вопроса (он ничего не пишет). Пользователю во время ожидания не писать.
- Кап → п. 4 правил.
- `BLOCKED` в отчёте исполнителя → если блокер о сложности/непонятном коде → единственная эскалация на Sol по шагу 5 (если исполнитель уже Sol или фаза `hard: true` → кап → вопрос); если блокер о требованиях (противоречие спеке, нужен выбор продукта) → один вопрос пользователю с вариантами, затем, если ответ меняет спеку, правка спеки тем же путём (Opus → Astra, кап 3) и продолжение той же фазы с тем же исполнителем (счётчик не сбрасывается).
- `worker_done --outcome failed` без признаков недоступности → читать как BLOCKED.
- После рестарта Orca: алгоритм §«Состояние и возобновление»; `orphaned: true` у терминала трактуется по правилу выше (не отправлять, но и не считать процесс завершённым).

## Состояние и возобновление

Отдельной машины состояний нет. Состояние — frontmatter плана (`orca_run`, `status` плана и фаз) и git-история (коммиты фаз с `F<n>` в сообщении). Один алгоритм, на который ссылаются шаг 0, §«Сбои» и возобновление (пользователь называет план или slug):

1. `run-use --id <orca_run>`; закрыть отработавшие (settled) терминалы Run (п. 9).
2. Все фазы `done`, план `active` → шаг 7 (финальное ревью).
3. Первая фаза `pending` = F<n>. `worker-list --run <orca_run> --json` содержит не-settled Dispatch с title `<slug>/…-F<n>` → это живой писатель: ждать его через `check --wait` по правилам молчания §«Сбои»; новый исполнитель только после доказанного выхода старого (`liveness: exited` или собственное наблюдение выхода процесса). Дальше — после settle.
4. Дерево чистое и `git log --oneline -30` содержит коммит с префиксом `<type>(<slug>): F<n> ` (ровно тот, что даёт шаг 6) → поставить `done` (коммит `docs(<slug>): F<n> done`), вернуться к п. 2. Грязное дерево — сначала п. 5.
5. Дерево грязное → список файлов фазы: `git diff --name-only` без `docs/plans/<slug>.md` (метаданные координатора, в том числе незакоммиченный `implementer: sol`, не откатываются) плюс untracked из `git status --porcelain`, которые названы в плане/брифе фазы или в последнем отчёте исполнителя; остальные untracked в список не входят. Один вопрос с этим списком: «продолжить F<n> с текущими правками / откатить эти файлы: <список> (`git checkout -- <tracked>` и `rm` перечисленных untracked) / стоп». Если принадлежность файлов фазе неясна, список всё равно показывается, и решает пользователь. `git clean -fd` и stash не используются.
6. Иначе — F<n> с шага 4: исполнитель из `implementer` (поле пустое → по таблице ролей), свежий бюджет 3 раунда; `implementer: sol` → без эскалации. При «продолжить с правками» бриф получает строку «часть работы уже в дереве, см. `git diff`».

Быстрый путь не возобновляется: при обрыве задача запускается заново (грязное дерево → вопрос из шага 0).
