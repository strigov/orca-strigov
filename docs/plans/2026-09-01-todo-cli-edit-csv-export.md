## Goal

Расширить fixture-приложение двумя независимыми блоками, не меняя действующий контракт `add`/`list`/`done`.

Блок 1 добавляет в `spikes/fixture/todo.py` команды `remove ID` и `edit ID TEXT` и переводит выдачу идентификаторов на `max(id) + 1`, чтобы после удаления новый элемент не получал id уже существующего. Блок 2 создаёт отдельный модуль `spikes/fixture/todo_export.py` с собственным CLI, который читает то же хранилище (включая переопределение `TODO_FILE`) через публичные функции `todo.py` и печатает или записывает CSV с колонками `id,text,done`. Единственное исключение из правила «только публичные функции» — одобренная оператором защитная проверка пути `--out` (поправка F1-B1, контракт C6), которая не читает и не пишет элементы, а лишь сравнивает путь назначения с путём активного хранилища.

Блоки не пересекаются по файлам и исполняются как один `parallel_group: G1`.

## Acceptance criteria

- `python3 todo.py remove ID` в отдельном процессе печатает ровно один удалённый dict в текущем формате `repr(dict)`, возвращает код `0`, удаляет элемент из хранилища, а следующий отдельный `list` его больше не показывает.
- `python3 todo.py edit ID TEXT` печатает обновлённый dict с новым `text` и прежним значением `done`, возвращает код `0` и сохраняет позицию элемента в порядке хранилища.
- Неизвестный ID в `remove` и `edit` обрабатывается так же, как в `done`: необработанный `KeyError: ID` в stderr, ненулевой код выхода, пустой stdout и побайтово неизменённый файл хранилища.
- После `remove` следующий `add` выдаёт `max(существующие id) + 1`, а для пустого, отсутствующего или повреждённого хранилища — `1`; выданный id никогда не совпадает с id, уже присутствующим в хранилище.
- `python3 todo_export.py` печатает в stdout CSV со строкой заголовка `id,text,done` и по одной строке на элемент в порядке хранилища; `--open` печатает только элементы с `done` равным `False`; `--out PATH` записывает тот же CSV в `PATH` и не печатает в stdout ничего.
- `todo_export.py` читает то же хранилище, что и `todo.py`, включая путь из `TODO_FILE`, не изменяет `todo.py` и не изменяет содержимое хранилища.
- `python3 todo_export.py --out PATH`, где `PATH` совпадает с активным `TODO_FILE` или указывает на тот же файл через симлинк либо хардлинк, завершается ненулевым кодом, печатает ровно одну строку в stderr, ничего не печатает в stdout, не создаёт и не открывает файл назначения на запись, а байты хранилища остаются прежними.
- Существующие `add TEXT`, `list [--open]`, `done ID`, их вывод `repr(dict)` и код `0` не меняются; `python3 -m pytest -q spikes/fixture/tests` проходит целиком.

## Contracts

### C1. Существующая публичная поверхность `todo.py` (проверено на `9ea5050`, изменению не подлежит)

```python
def add(text: str) -> dict: ...
def complete(item_id: int) -> dict: ...
def list_items(show_done: bool = True) -> list[dict]: ...
def main(argv: list[str] | None = None) -> int: ...
```

`list_items(show_done=True)` возвращает все элементы в порядке хранилища; `list_items(show_done=False)` возвращает только элементы с `item["done"] is False`, порядок сохраняется. Функция ничего не пишет и не создаёт файл. Это единственная публичная функция чтения — фаза Ф2 обязана использовать её и не имеет права обращаться к приватным именам, кроме одобренного оператором вызова `todo._storage_path()` в защитной проверке `--out` (C6), который элементы не читает.

### C2. Разрешение пути и форма хранилища (проверено, изменению не подлежит)

Путь определяется приватным `_storage_path()` при каждом вызове: непустая переменная окружения `TODO_FILE` даёт `Path(value).expanduser()`, иначе используется `spikes/fixture/todo.json` рядом со скриптом. Оба модуля видят один и тот же путь, потому что `todo_export.py` вызывает функции `todo.py`, а не считывает окружение сам: в том числе и путь активного хранилища для защитной проверки `--out` он получает вызовом `todo._storage_path()` (C6), а не чтением `TODO_FILE`. Ф1 `_storage_path()` не изменяет.

Файл — UTF-8 JSON, верхний уровень — список объектов:

```json
[
  {"id": 1, "text": "x", "done": false}
]
```

Корректный элемент имеет ровно ключи `id`, `text`, `done` с `type(id) is int`, `type(text) is str`, `type(done) is bool`. Отсутствующий, пустой, whitespace-only, синтаксически повреждённый или структурно неверный файл читается как `[]`. Все изменяющие операции пишут полный список атомарно через temp-файл в каталоге цели и `os.replace`.

### C3. Существующий CLI-контракт (изменению не подлежит)

- `python3 todo.py add TEXT` → одна строка `{'id': 1, 'text': 'x', 'done': False}\n`, код `0`.
- `python3 todo.py list` → по одному `repr(dict)` на строку в порядке хранилища; пустое хранилище не печатает ничего; код `0`.
- `python3 todo.py list --open` → только элементы с `done` равным `False`.
- `python3 todo.py done ID` → одна строка обновлённого `repr(dict)` с `'done': True`, код `0`.
- `python3 todo.py done <неизвестный ID>` → необработанный `KeyError: <ID>`, traceback в stderr, пустой stdout, код выхода `1` (проверено на `9ea5050`), хранилище не переписывается.

Никаких заголовков, префиксов и дополнительных сообщений CLI не печатает.

### C4. Новая поверхность Ф1 в `todo.py`

```python
def _next_id(items: list[dict]) -> int: ...
def remove(item_id: int) -> dict: ...
def edit(item_id: int, text: str) -> dict: ...
```

- `_next_id(items)` возвращает `max((item["id"] for item in items), default=0) + 1`. Для пустого списка результат `1`.
- `add(text)` меняет только источник идентификатора: `{"id": _next_id(items), "text": text, "done": False}`. Сигнатура, порядок добавления в конец списка, атомарная запись и возвращаемый dict не меняются. Для последовательности добавлений без удалений выдача остаётся `1, 2, 3, …`, поэтому наблюдаемое поведение существующих тестов сохраняется.
- `remove(item_id)` загружает список, находит **первый** элемент с данным `id`, удаляет его из списка, атомарно сохраняет оставшийся список и возвращает удалённый dict (в том виде, в каком он был в хранилище, включая текущее значение `done`). При отсутствии `id` выбрасывает `raise KeyError(item_id)` и не переписывает файл.
- `edit(item_id, text)` загружает список, находит **первый** элемент с данным `id`, присваивает `item["text"] = text`, сохраняет позицию элемента и значение `done`, атомарно сохраняет список и возвращает изменённый dict. При отсутствии `id` выбрасывает `raise KeyError(item_id)` и не переписывает файл.

Поиск «первого совпадения» повторяет действующее поведение `complete()`; дубликаты `id` возможны только при ручной правке файла и специально не обрабатываются.

### C6. Новая поверхность Ф2 — `spikes/fixture/todo_export.py`

Публичные имена модуля — ровно два:

```python
def write_csv(stream: TextIO, show_done: bool = True) -> None: ...
def main(argv: list[str] | None = None) -> int: ...
```

- Модуль импортирует только стандартную библиотеку (`argparse`, `csv`, `os`, `sys`, `pathlib.Path`, `typing.TextIO`) и `import todo`. `os` и `Path` нужны исключительно защитной проверке `--out` ниже. При запуске `python3 todo_export.py` каталог скрипта попадает в `sys.path[0]`, поэтому `import todo` разрешается независимо от текущего рабочего каталога.
- `write_csv(stream, show_done)` — публичная сигнатура не меняется: функция сама читает элементы вызовом `todo.list_items(show_done=show_done)`, пишет строку заголовка `("id", "text", "done")`, затем для каждого элемента строку `(item["id"], item["text"], item["done"])` — в порядке, который вернула `list_items`. Заголовок пишется всегда, в том числе когда элементов нет. Функция ничего не возвращает и не изменяет хранилище.
- Тело записи вынесено в приватный `_write_rows(stream: TextIO, items: list[dict]) -> None`: он создаёт `csv.writer(stream, lineterminator="\n")`, пишет заголовок `("id", "text", "done")`, затем строку `(item["id"], item["text"], item["done"])` для каждого элемента `items` в переданном порядке; заголовок пишется всегда, в том числе когда `items` пуст; хранилище он не читает и не изменяет. `write_csv()` реализуется как тонкая обёртка `_write_rows(stream, todo.list_items(show_done=show_done))`. `_write_rows` — строго внутренняя деталь модуля: в публичную поверхность он не входит, из CLI не адресуется и тестами не вызывается; он введён поправкой F1-B1 ровно затем, чтобы `main()` мог записать уже прочитанные элементы, не читая хранилище второй раз.
- Элементы для CLI читает `main()` вызовом `todo.list_items(show_done=not ns.open)` и передаёт их в `_write_rows()`. Разделение чтения и записи введено одобренной оператором поправкой F1-B1: чтение хранилища обязано полностью завершиться **до** открытия `--out` на запись. Публичная сигнатура `write_csv()`, набор колонок, строка заголовка, порядок строк, диалект и правила экранирования при этом не меняются; наблюдаемое поведение CLI тоже не меняется.
- Значения `done` сериализуются дефолтным преобразованием `csv.writer` для `bool`, то есть строками `True` и `False` (не `true`/`false`), что согласуется с существующим выводом CLI `repr(dict)`. Экранирование — дефолтное `csv.QUOTE_MINIMAL`.
- **Защита `--out` от перезаписи активного хранилища (поправка F1-B1, одобрена оператором).** До открытия `--out` на запись `main()` узнаёт путь активного хранилища вызовом приватной `todo._storage_path()` — это единственное разрешённое Ф2 обращение к приватным именам `todo.py`, и оно используется только для сравнения путей. Назначение считается совпадающим с хранилищем, если `Path(ns.out).resolve() == Path(todo._storage_path()).resolve()` либо, когда `--out` уже существует (и существует сам файл хранилища), истинно `os.path.samefile(ns.out, storage)`. `samefile()` вызывается только при существовании обоих путей: на отсутствующем файле он поднял бы `OSError`, а пустое или ещё не созданное хранилище — штатный сценарий экспорта.
- При срабатывании защиты `main()` печатает в `sys.stderr` **ровно одну** строку `todo_export: refusing to overwrite the active storage: <ns.out>` и возвращает `2`; файл назначения не открывается и не создаётся, в stdout не печатается ничего, хранилище остаётся побайтово неизменным. Ни traceback, ни дополнительная диагностика, ни ветки восстановления или перезаписи контрактом не предусмотрены; конкретное значение `2` — деталь реализации, тесты проверяют только «код ≠ 0» и «ровно одна строка в stderr».
- `main(argv)` разбирает `argparse.ArgumentParser(prog="todo_export")` c `p.add_argument("--out")` и `p.add_argument("--open", action="store_true")`, затем выполняет строго следующий порядок шагов:
  1. читает элементы: `items = todo.list_items(show_done=not ns.open)` — всегда до любого открытия файла на запись;
  2. если `ns.out` задан — выполняет защитную проверку выше и при совпадении возвращает `2`, ничего не записав;
  3. без `--out`: `_write_rows(sys.stdout, items)`; с `--out PATH`: `open(ns.out, "w", encoding="utf-8", newline="")` и `_write_rows(handle, items)`, в stdout не печатается ничего;
  4. возвращает `0`.
- Файл завершается блоком `if __name__ == "__main__": sys.exit(main())` — так же, как `todo.py`.

Наблюдаемый вывод для хранилища `[{"id":1,"text":"x","done":true},{"id":2,"text":"плов","done":false}]`:

```
id,text,done
1,x,True
2,плов,False
```

Для `--open` того же хранилища:

```
id,text,done
2,плов,False
```

Для пустого, отсутствующего или повреждённого хранилища — только строка заголовка `id,text,done\n`, код `0`.

Текст, содержащий разделитель или кавычку, экранируется правилами `csv`: `a,b "q"` даёт поле `"a,b ""q"""` (проверено на Python 3.10.11).

### C7. Межфазная зависимость

Ф2 потребляет только контракты C1 и C2, существующие и проверенные на `9ea5050` (включая `_storage_path()` из C2, который Ф1 не трогает); ничего из C4/C5 она не использует. Ф1 не потребляет ничего из Ф2. Поэтому фазы стартуют одновременно, а слияние их веток не создаёт ни текстового, ни семантического конфликта: единственная общая поверхность — `list_items()` и форма JSON, и обе Ф1 не меняет.

## Test strategy

Общая обвязка обеих фаз уже существует и не меняется: `spikes/fixture/pytest.ini` (`testpaths = tests`, `addopts = -p no:cacheprovider`) и `spikes/fixture/conftest.py` (добавляет каталог fixture в `sys.path`). Ни один тест не создаёт и не трогает `spikes/fixture/todo.json`.

Новые тесты:

Не тестируется: точный текст traceback, argparse-ошибки для нечисловых ID, отсутствующие аргументы, дубликаты `id` в хранилище, конкурентные процессы.

### Ф2 — `spikes/fixture/tests/test_export.py`

Хранилище в тестах засеивается двумя способами: прямой записью JSON по форме C2 (детерминированно и полностью независимо от Ф1) и — в одном интеграционном тесте — реальными вызовами `todo.py` в подпроцессе, чтобы доказать, что оба модуля читают один и тот же `TODO_FILE`.

1. **stdout, все элементы, порядок хранилища** — засеять `[{1,"x",true},{2,"y",false},{3,"плов",false}]`; `python3 todo_export.py` даёт stdout ровно `"id,text,done\n1,x,True\n2,y,False\n3,плов,False\n"`, код `0`, пустой stderr.
2. **`--open`** — то же хранилище, `--open` даёт ровно `"id,text,done\n2,y,False\n3,плов,False\n"`.
3. **`--out PATH`** — `--out out.csv` даёт пустой stdout, код `0`, а `out.csv` (чтение с `newline=""`, `encoding="utf-8"`) равен полному CSV из теста 1; отдельная проверка `--out out_open.csv --open` даёт CSV из теста 2. Файл хранилища после экспорта побайтово не изменился.
4. **экранирование** — элемент с текстом `a,b "q"` даёт строку `1,"a,b ""q""",False`.
5. **пустое и повреждённое хранилище** — для отсутствующего файла и для файла с содержимым `"{"` stdout равен ровно `"id,text,done\n"`, код `0`, stderr пуст; повреждённый файл не переписывается.
6. **общее хранилище с `todo.py`** — отдельными процессами `python3 todo.py add "x"`, `python3 todo.py add "y"`, `python3 todo.py done 1` при том же `TODO_FILE`, затем `python3 todo_export.py` даёт `"id,text,done\n1,x,True\n2,y,False\n"`, а `--open` — `"id,text,done\n2,y,False\n"`.
7. **`--out` не разрушает активное хранилище** (поправка F1-B1) — межпроцессный тест, где `TODO_FILE` и `--out` указывают на один и тот же путь: засеять хранилище `[{1,"x",true},{2,"y",false}]`, прочитать его байты, выполнить `python3 todo_export.py --out <тот же путь>` и проверить, что код возврата отличен от `0`, stdout пуст, stderr состоит ровно из одной строки, а байты файла хранилища совпадают со снятыми до запуска. Точный текст строки stderr не проверяется — только то, что строка ровно одна.

Цикл фазы: `python3 -m pytest -q spikes/fixture/tests/test_export.py`, затем `python3 -m pytest -q spikes/fixture/tests`.

Не тестируется: текст с внутренним переводом строки, поведение при отсутствующем родительском каталоге `--out`, права доступа, кодировки помимо UTF-8, диалекты CSV, окончания строк на не-POSIX платформах, а также алиасы `--out` через симлинк и хардлинк и гонка TOCTOU между проверкой и открытием файла: контракт C6 их описывает, но одобренная поправка предусматривает ровно один новый тест — на совпадающий путь.

## Risks / unknowns / assumptions

- **Представление `done` в CSV.** Пользователь задал колонки, но не формат булева значения. План фиксирует дефолтное поведение `csv.writer` — `True`/`False` — как согласованное с текущим выводом CLI `repr(dict)`; JSON-подобные `true`/`false` сознательно отвергнуты. Это решение планировщика, а не требование пользователя.
- **Окончания строк.** Дефолтный `lineterminator` у `csv.writer` равен `\r\n`; план явно фиксирует `lineterminator="\n"` и `newline=""` при открытии файла, иначе межпроцессные сравнения stdout стали бы платформозависимыми. `sys.stdout` открыт с `newline=None`, поэтому `\n` транслируется в `os.linesep`; на проверенном окружении (macOS, Python 3.10.11) это тот же `\n`. На Windows тесты 1–3 и 5–6 из Ф2 не гарантированы; поддержка Windows не заявлена.
- **Поведение `--out` при ошибке.** Отсутствующий родительский каталог даёт необработанный `OSError` и ненулевой код — то же самое, что делает `todo.py` при неверном `TODO_FILE`. Согласовано с уже зафиксированным non-goal предыдущего плана. Единственное исключение из этого стиля — совпадение `--out` с активным хранилищем: там C6 требует не traceback, а ровно одну строку в stderr и код `2`.
- **Защита `--out` от перезаписи хранилища (поправка F1-B1).** Проверка сравнивает `Path(...).resolve()` и, когда оба пути существуют, `os.path.samefile()`; этого достаточно для совпадающего пути, симлинка и хардлинка, но проверка не транзакционна: между ней и `open()` остаётся окно TOCTOU, а экзотические алиасы (bind-mount, сетевые ФС с несовпадающими inode) она не различает. Смягчение — обязательный порядок из C6: элементы читаются через `list_items()` до открытия `--out`, поэтому даже при промахе проверки данные уже в памяти и попадают в CSV. Блокировки, повторная проверка после открытия и атомарная запись CSV сознательно не вводятся — см. отложенные пункты про конкурентных писателей и про режим записи `--out`.
- **Изменение правила выдачи id.** Переход с `len(items) + 1` на `max(id) + 1` меняет внутреннюю логику `add()`, но не наблюдаемое поведение для последовательности добавлений без удалений; оба существующих теста `test_cli.py` остаются зелёными без правки. Ранее созданные вручную хранилища с «дырами» после этой правки перестают выдавать дубликаты — это и есть требование пользователя.
- **Дубликаты `id`.** Возможны только при ручной правке JSON. `remove`/`edit` действуют на первое совпадение, повторяя `complete()`; отдельная валидация не вводится.
- **Дублирование тестовой обвязки.** `_run_cli()` и `_run_export()` почти совпадают, но `conftest.py` не входит ни в одну фазу, и вынос общего хелпера нарушил бы требование непересекающихся наборов файлов. Дублирование принято сознательно; ревьюеру не следует считать это дефектом.
- **Параллельное слияние.** Файловых конфликтов нет по построению. Семантический риск ограничен `list_items()` и формой JSON, которые Ф1 не меняет; страховкой служит команда `python3 -m pytest -q spikes/fixture/tests`, прогоняемая на слитом дереве.
- **Поведение `verify` в разных деревьях.** `bin/verify-gate` выполняет все команды из frontmatter в любом дереве, включая worktree фазы Ф1 и BASE-worktree, где `spikes/fixture/tests/test_export.py` ещё не существует; голый `pytest <путь>` там завершился бы кодом `4` («file or directory not found»). Поэтому третья команда обёрнута в `[ -f ... ]` и в таком дереве является определённым no-op с кодом `0`. Первая команда собирает каталог целиком и потому автоматически подходит и обеим фазам, и слитому дереву.
- **Отсутствие lint/typecheck.** В окружении нет `ruff`, `flake8`, `mypy`, а в репозитории нет `pyproject.toml`, `setup.cfg`, `tox.ini` и `Makefile`; единственная воспроизводимая проверка — pytest-прогон fixture. Список `verify:` намеренно ограничен им.
- **Окружение.** Проверено локально: Python `3.10.11`, pytest `9.0.3`, `python3 -m pytest -q spikes/fixture/tests` из корня репозитория — 7 passed. Сторонние зависимости не вводятся.
